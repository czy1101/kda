## 3. 执行组织、寄存器与任务调度

### 3.1 CU、CE 与 Warp32

一个 block 整体分配到一个 CU，使用该 CU 上的寄存器、Shared 和执行资源。CE 是 CU 之上的共享域，其中多个 CU 共享 L2；LLC 则服务多个 CE。编程模型采用 Thread→Warp→Block→Grid，Warp 含 32 个线程。

对归约、softmax、RMSNorm：先考虑让一行或若干行映射到 Warp/Block，减少跨 Warp Shared 交换。短行若只用少量 lane，要同时考虑把多行放入同一 block 的布局代价。

线程块大小优先测试 32 的倍数；非倍数不等于非法，但最后一个 Warp 会有闲置 lane。2D/3D block 的 Warp 编号应根据**线性线程 ID**计算：

```cpp
int linear_tid = threadIdx.x + blockDim.x *
                 (threadIdx.y + blockDim.y * threadIdx.z);
int lane = linear_tid & 31;
int warp = linear_tid >> 5;
```

Grid 中的 block 顺序和同时驻留都没有普遍保证，不能依赖普通 block 间自旋来实现任意全局 barrier。[HGGC 硬件模型与线程层次](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=611#13-ppu硬件模型)。

### 3.2 VREG、SREG 与 uniform 路径

VREG 保存每线程数据；SREG 保存 Warp 内公共状态。公共循环上界、page 基址、行跨度、统一分支可减少重复向量计算。编译器是否真正采用 SREG，必须检查产物，不能从源代码中的标量变量声明推断。

HGGC 提供 `__builtin_ppu_to_uniform_b32()`。只有当其语义前提成立、相关 lane 的值本来就相同时，才考虑使用；它不能把真实不同的 per-lane 数据“优化”为相同值。控制流和 Warp 协作指令的 uniform 要求也不是简单增加一次广播就一定满足。

使用 Asight 检查 VREG/SREG、相关指令和 SREG 读取停顿；SREG 也可能成为资源或端口瓶颈。[HGGC uniform 内建](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=611#52137-builtin_ppu_to_uniform_b32)。

### 3.3 资源、驻留与尾波

实际驻留同时受线程、block、寄存器、Shared、分配粒度及实现约束限制。以下仅为预算框架，分子必须使用本机已核验口径：

```text
寄存器需求/block ≈ 每线程向量寄存器条目 × block线程数
Shared需求/block = 静态Shared + 动态Shared + 各stage缓冲
驻留block上界 ≤ min(线程限制, 寄存器限制, Shared限制, block限制)
```

高 occupancy 不等于最优：过小 tile 降低复用，过度压寄存器可能引入 spill，增加 stages 又可能压低驻留。动态索引数组、过深展开、长生命周期累加器都可能产生 local/stack 访问；local 是设备内存支持的线程私有空间，并非片上 Shared。

小 batch decode、窄矩阵、少专家任务还要考虑 CU 空闲和尾波。优先依据实际 grid/驻留评估沿 token/head/输出维增加并行的必要性；split-K 需要计入合并、原子或 workspace 成本。[优化指南：资源与 spill](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=832)。

## 4. 高效计算路径

### 4.1 Tensor Cell：原生矩阵乘加

**文档支持**：`ppu001` 使用 `tc01` 执行 `D=A×B+C`。Warp 的所有参与线程共同持有 fragment，不是每个线程独立得到一整块矩阵。适合规则 GEMM、Attention 的 QK/PV、MLP 和卷积映射。

| 输入类型 | 文档列出的原生 shape `(M,N,K)` | 累加/输出说明 |
| --- | --- | --- |
| FP16、BF16 | `(16,16,16)`、`(16,16,8)`、`(8,16,16)`、`(8,16,8)` | 有 FP32 累加形式，也有同低精度形式；前端可暴露子集 |
| FP32、TF32 | `(16,16,8)`、`(16,16,4)`、`(8,16,8)`、`(8,16,4)` | FP32 累加；FP32/TF32 的数值语义不可混淆 |
| signed/unsigned INT8 | `(16,16,32)`、`(16,16,16)`、`(8,16,32)`、`(8,16,16)` | INT32；注意符号组合、溢出和饱和模式 |

这些是 **TIX 直接列出的片段**，不能据此断言任意 Triton tile 可编译。`tc01.ex` 则是软件扩展 shape，文档明确它与原生 shape 存在性能差别，不能当成同等代价的原生矩阵指令。[TIX tc01 MMA](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=612#9310-ppu001-tensor-cell-指令-pputc01mma)。

### 4.2 怎样触发矩阵计算

从最能表达任务、且已安装可用的入口选择：

1. **算子库**：acBLAS/适配库建立正确性和性能参考；库存在不代表所有布局都选中最快 kernel。
2. **ACTLIZE**：用 `PPU0010` tag、PPU 对应 MMA/Copy atom 和 collective 组织矩阵与搬运；注意同仓库也含另一代实现。
3. **HGGC C++**：`hggc_mma.h` 中 `awmma::fragment/load_matrix_sync/mma_sync/store_matrix_sync`。其允许的 shape、类型组合以该 API 自己的表为准。
4. **Triton**：使用本机 `triton-for-sail`；对 `tl.dot` 的支持、矩阵模式、AIU 自动选择逐个检查当前后端，不能搬用天数后端 `stride=` 等扩展。
5. **Inline TIX**：高层不能表达且任务允许时，使用匹配 `ppu001` 的 `tc01`；负责 fragment 映射、约束、参与 lane 与内存布局。

HGGC `awmma` 的关键条件：warp 全员一致调用；`load/store_matrix_sync` 的起始指针按 256 bit（32 B）对齐；FP16 的 `ldm` 为 8 元素倍数，float 为 4 元素倍数。`ldm` 是元素跨度，不是字节。TF32 入口另有 `__float_to_tf32` 和 `precision::tf32` 约束。

WMMA 兼容接口允许的逻辑 shape 不等于底层一条指令的 shape；查看 lowering 是否需要额外片段重排。最终同时检查矩阵指令、前后转换、搬运与寄存器压力。

来源：[HGGC Warp 矩阵函数](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=611#527-warp矩阵函数)、[ACTLIZE 官方源码](https://github.com/t-head/actlize/tree/v1.0.0)、[Triton 适配指南](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=46&chapterId=758)。

#### 本机矩阵路径、精度与实际 PASM

**本机已验证**：逻辑设备 0，`64×64×64` GEMM，tile `32³`，grid `(2,2)`，4 warps、1 stage，K-loop 两次；浮点输出/累加为 FP32，INT8 为 INT32。CPU 参考使用量化后输入转 FP32/INT32 再矩阵乘；浮点门限 `atol=0.05, rtol=0.03`，INT8 要求完全一致。随机种子 27，INT8 输入为 `[-3,3]`。全部输出对拍通过：

| 输入与精度模式 | 实际计算指令 | 最大绝对误差 | `n_regs` | Shared/block |
| --- | --- | ---: | ---: | ---: |
| FP16，`ieee` | `v.mma.f32.f16.m16n16k16` | 1.3351440e-5 | 60 | 4096 B |
| BF16，`ieee` | `v.mma.f32.bf16.m16n16k16` | 6.6757202e-6 | 60 | 4096 B |
| FP32，`ieee` | **普通 `v.fma.f32.rtte`，未发现 `v.mma`** | 0 | 66 | 8192 B |
| FP32，`tf32` | `v.mma.f32.tf32.m16n16k8` | 0.0237293243 | 62 | 8192 B |
| INT8 | `v.mma.i32.i8.i8.m16n16k32` | 0，完全一致 | 46 | 4096 B |

五组 `n_spills=0`。FP32 `ieee` 汇编含 256 个静态 FMA 位置，这不是整次 kernel 的动态计数。`tf32` 数值通过本探针较宽门限，不代表满足实际模型的误差门限。没有采正式性能，不公布加速比。

**优化含义**：在这版 FlagTree 上，`tl.dot` 加 FP32 `ieee` 不保证触发 Tensor Cell；改为 `tf32` 会改变计算路径与误差。不能为使用矩阵单元擅自降低任务精度，也不能从这个小核推断所有 FP32 dot 均退化。FP16/BF16/INT8 所测普通 load→dot 路径使用 Global/TSM staging，汇编未发现 AIU，矩阵指令出现不等于搬运单元也已触发。

### 4.3 2:4 结构化稀疏矩阵

**文档支持**：`ppu.tc01.mma.sp`，本版 TIX 指南规定 **A 为稠密矩阵、B 为 2:4 稀疏矩阵**。B 沿指定列方向的相邻 4 元素 chunk 保留最多两个非零位置，压缩值和 metadata 配套。

触发需要：

- B 满足规定的稀疏模式，并按相应 dtype/shape 的 fragment 布局压缩。
- 正确生成位置 metadata，并按 Warp group 约定传递 `psel`、`ssel`。
- 指令、类型、shape、累加器和 Warp 一致执行条件全部合法。

这不是任意 sparse mask、Block Sparse Attention 或输入里恰好很多 0 就会自动获得的加速。若模型本来不满足 2:4，修改权重结构需要单独的模型精度依据；预处理、metadata 读取和反复消费次数都要计入收益。文档支持不代表用户安装的 Triton/库已开放该入口。[TIX 稀疏 tc01](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=612#94-ppu001-tensorcell-指令稀疏矩阵)。

### 4.4 打包半精度算术与 FMA

**文档支持**：TIX 的 `.f16x2/.bf16x2` 将一个 32-bit operand 当两个 16-bit 元素，支持配对运算；`ppu.fma` 对两路分别做融合乘加，不是两项内积。FP16/BF16 packed add、sub、mul 与 FMA 在手册中均标注支持 `ppu001`。

高层入口包括 `__half2`、`__ppu_bfloat162` 及对应内建；例如 Math API 有 `__hadd2`、`__hmul2`、`__hfma2`。应从目标版本头文件核对具体重载。普通 `a*b+c` 是否融合、是否打包取决于精度提升、布局和编译选项，不能只看表达式。

适合逐元素 scale/bias、量化/反量化与激活融合。半精度中间舍入、FMA 一次舍入、`.ftz/.sat/.relu` 会改变数值行为；验证 NaN/Inf、次正规数、符号零和实际模型数值范围。归约仍按所需累加精度实现。

检查转换、pack/unpack、加载宽度与尾元素处理的总开销；一条 packed 操作不等于整个算子快两倍。[TIX 半精度 FMA](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=612#ppu-fma-half)、[Math API](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=617)。

**本机已验证触发写法**：Triton load 后保持 FP16/BF16，显式 `tl.fma(a,b,c)` 再 store；4096 元素、BLOCK=1024、4 warps，分别生成 **`v.fma.f16x2` / `v.fma.bf16x2`**，两组均 `n_regs=32, n_spills=0`。4096 个结果分别与 CPU FP64 计算后舍入回目标类型的参考完全一致；只覆盖该组有限随机输入，不推断所有特殊值和边界。普通 `a*b+c` 的融合行为及峰值尚未测。

### 4.5 整数点积、字节排列和位操作

| 路径 | 计算或整理的内容 | 用途与限制 |
| --- | --- | --- |
| `ppu.dp4a` | 两个 32-bit operand 各取四个 8-bit 分量，点积加到 32-bit accumulator | 小粒度 INT8 点积；符号解释按各 operand 修饰符 |
| `ppu.dp2a.lo/hi` | 两个 16-bit 分量与指定半段的两个 8-bit 分量点积累加 | 混合打包整数；不能复用别的厂商的支持/失败结论 |
| `ppu.prmt` | 两个寄存器内的字节选取与排列 | INT8/INT4 解包、bit-layout 整理；不是跨 lane shuffle |
| `popc/brev/bfe/bfi` 等 | 位计数、反转、提取与插入 | mask、路由、索引、量化 metadata |
| 宽乘/乘积高位 | 整数完整或高位乘积 | 地址与整数算法；匹配 signed/unsigned 语义 |

以上为 TIX/SDK 接口层能力；不承诺各条均一对一映射原生 ISA，也不提供未经测试的每周期吞吐。实际 source→IR→PASM 以及负数、边界、溢出对拍后才能纳入性能候选。[TIX 位操作与整数点积](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=612#6-位级操作与数据变换)。

### 4.6 数学函数、SFU 和精度模式

先区分标准库函数、快速 intrinsic、TIX 近似操作及最终 SFU 指令。TIX 有 `ex2/lg2/rcp/rsqrt/sqrt/tanh` 等接口，但**高层函数或一条 TIX 不必然只对应一次物理 SFU 操作**。

softmax 可考察 `exp2` 与缩放融合，Norm 可考察 `rsqrt`；除法、精确 sqrt、三角函数的高精度实现可能带额外修正。快速数学仅在误差要求允许时使用，不把 `rintf` 和 `roundf` 这类不同舍入语义的函数直接互换。

`--use_fast_math` 及 `--ftz/--prec-div/--prec-sqrt/--fmad` 会影响数值和 lowering。按小量、极值、NaN/Inf、次正规数与实际输入范围验证；保存所用参数。避免浮点常量或重载无意提升至 double；索引能证明 32-bit 安全时可减少不必要 i64，但指针寻址仍遵守平台位宽。

验证使用 PASM 的整体序列和 Asight SFU/FALU 活跃度；管线利用率不是某个函数的精确动态次数。[优化指南：指令与精度](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=832)、[Math API](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=617)。

## 5. 数据搬运：高效路径与触发条件

### 5.1 数据通路总览

| 从哪里到哪里 | 可用入口 | 应重点检查 |
| --- | --- | --- |
| Global↔寄存器 | 普通指针、向量 load/store、TIX `ld/st` | 合并、对齐、mask、缓存策略、地址生成 |
| Global→Shared，小段 | `ppu.cp.async` 及高层异步 copy | 合法大小、commit/wait、是否绕过寄存器中转 |
| Global→Shared，张量 tile | `ppu001` AIU bulk copy | 尺寸/坐标、swizzle、padding、转置与 consumer |
| Shared→矩阵 fragment | `tc01.ldmatrix` 或匹配 AIU 的 `ldmatrix.swzl` | 参与 Warp、lane-layout、tile 与 bank/group |
| 寄存器↔Shared | 普通 Shared 指针读写 | producer/consumer 布局、同步、复用收益 |
| Warp 内寄存器交换 | shuffle/vote/redux | mask、width、参与线程和数据依赖 |
| Host↔Device、Device↔Device | runtime copy/DMA、P2P、通信库 | NUMA/pinned、拓扑、依赖及真实重叠 |

### 5.2 元素级异步拷贝 `ppu.cp.async`

**文档支持**：非阻塞 Global→Shared。大小为 1/2/4/8/16 B；不同形式的可选参数不同。源/目的指针对齐必须满足所选大小。4/8/16 B 形式可带有效源长度或忽略源的参数，未读取部分可填零；越界源长度不是合法 mask。

高层可用 `hggc::memcpy_async`、`cooperative_groups::memcpy_async` 配合 barrier/pipeline/协作组等待。只有生成的路径确实使用异步硬件，才能说避免了普通寄存器中转。

关键完成规则：通过 `commit_group` 提交，再用 `wait_group/wait_all` 等待。单独 `__syncthreads()` 不能替代异步完成保证；跨线程消费时还需满足可见性和块内协作要求。buffer 被下一轮覆盖前，必须确认上一轮消费者完成。

`.ca` 对这条 copy 的定义是缓存在 L2/LLC，**不包含 L1**，与普通 `ld.ca` 的层级范围不同。`.LLC::128B/256B` 的额外预取粒度修饰仅属 `ppu0015+`，810E 不使用。[TIX 非 bulk 拷贝](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=612#762-非批量拷贝指令ppucpasync)。

### 5.3 AIU：810E 的张量搬运单元

**是什么**：CU 内负责批量张量搬运的硬件机制。Warp 级异步操作将 Global tile 装入 Shared，由硬件承担一部分寻址、边界处理和布局组织，适合给 Tensor Cell 连续供数。

**810E 版入口**：`ppu.cp.async.aiu.bulk.tensor.shared.global...`。本代具体语法支持 `.2d/.3d`，搬运元素宽度 `.b8/.b16/.b32`；连续/更低维任务是否用退化维度实现，按封装与实际探针确认，不另造一条“原生 1D 语法”。

**触发时必须明确**：

- Tensor 维度、Cube 起始坐标、Cube 各维大小和实际地址范围。
- Global 源地址和 Shared 目标地址；Warp 的参与和参数一致性。
- 默认 swizzle 或 linear 写入模式，以及下游矩阵读取模式。
- H/W 越界的 zero/neighbor padding；C 方向仅 zero padding。
- `.b16/.b32` 的 H/W 转置支持；`.b8` 不按此形式支持转置。
- `.stride1/.stride2` 与 `.stride/.zfill` 各自是读取步长还是写入插零，不把它当任意 pitch。
- 提交、等待、可见性与阶段 buffer 生命周期。

**Shared 规划不能只按逻辑 tile 元素数计算**：

| `ppu001` AIU 约束 | 需要落实的内存安排 |
| --- | --- |
| swizzle 目标起点 | 128 B 对齐 |
| linear 目标起点 | 文档要求 4 B 对齐；其余指令/消费者限制仍需满足 |
| C 方向分片 | 按 32 B slice 向上补齐，最多 4 slices，即 128 B/条 |
| C 方向超过 128 B | 多条 AIU 指令分片，不能只增加 `cube_c` |
| swizzle 行批量 | `cube_n*cube_h*cube_w` 按 8 的倍数预留跨度；补足的行并非全部被硬件写入 |
| consumer | swizzle 数据使用匹配的 `tc01.ldmatrix.swzl` 解释；不能当普通行连续数组读取 |

`.swzl` 与 `.linear` 的参数表述在手册个别位置存在未完全展开的字段说明；实现时应从目标版本的 ACTLIZE Copy atom、头文件和最小正确样例确认，不猜测隐藏操作数。

**用途与收益验证**：在 GEMM/Attention 的 staging 中减少逐 lane 的 load、Shared store、地址算术和中间寄存器；同时检查 padding 容量、多条 copy、swizzle consumer 和等待带来的代价。AIU 不等于“任意二维 load 自动加速”。

来源：[ppu001 AIU 指令与约束](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=612#7631-ppu001-cpasyncaiu)、[Swizzle 规则](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=612#7632-ppu001-swizzle-模式)。

#### 本机 AIU linear 最小正确路径

**本机已验证**：当前 SDK 的 `<hggc_aiu.h>` 暴露 `aiu::cube_load_params`、`aiu::tsm_load_cube`；下列 kernel 经 `hgcc -arch=ppu_10 -O3` 编译并以 `<<<1,32>>>` 运行。Tensor 为 FP32 `[1,8,16]`、Cube 同形，共 128 元素，输入为 `float(i)-61`，全部输出与输入完全一致：

```cpp
#include <hggc_runtime.h>
#include <hggc_aiu.h>

__global__ void aiu_linear_copy(const float* input, float* output) {
    __shared__ __align__(128) float tile[128];
    aiu::cube_load_params p(1,8,16, 0,0,0, 1,8,16,1);
    aiu::tsm_load_cube<aiu::zero_padding,
                       aiu::no_transpose, aiu::linear>(tile, input, p);
    asm volatile("ppu.cp.async.commit_group;" ::: "memory");
    asm volatile("ppu.cp.async.wait_all;" ::: "memory");
    __syncthreads();
    for (int i=threadIdx.x; i<128; i+=blockDim.x)
        output[i]=tile[i];
}
```

`hgobjdump --isa` 显示 **`vmem.aiu.ld.tsm.l1.t0.p0.s0.m0.3d.b32.kp1`**、`s.wait commit_group(0)`，并在消费端使用普通 `tsm.ld.b32`。这证明本机存在可编译、可执行且结果正确的 AIU Global→TSM **linear** 路径；不证明 swizzle/转置/越界 padding 的全部组合，也没有证明与计算重叠或比普通 copy 更快。这里的 `l1/kp1` 名称不单独作为缓存命中或物理路径结论。

当前安装的 Triton 后端源码有 `add_tle_promote_async_load_to_aiu`、`add_aiu_lowering` pass；这只是实现线索。前述普通 dot 探针没有 AIU 指令，不能从 pass 存在宣称自动触发。TLE 扩展仍按任务启用和项目 API 核验规则使用。

### 5.4 异步流水、barrier 与实际重叠

双缓冲或多 stages 的必要条件是独立 buffer、正确生产/消费边界、有限的未完成请求，以及足够计算来覆盖传输。等待若紧跟在每次发起之后，接口虽异步，仍未证明有效重叠。

HGGC 文档提供异步 barrier、pipeline 和 TIX `awbar`。barrier 的 arrive/phase、copy 完成跟踪与线程同步是不同语义；不可从别的平台套用 mbarrier 大小、phase 或 fence 规则。优先使用目标 SDK 已正确封装的接口。

验证时同时看发起→提交→计算→等待→消费的顺序，检查 Shared/VREG 和驻留变化。计数器可说明等待/流量变化；具体计算-搬运重叠需要时间线或受控吞吐实验补证。[HGGC 异步屏障与流水线](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=611#45-异步屏障与流水线)、[TIX async-group](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=612#761-异步拷贝操作的完成机制async-group-机制)。

## 6. Shared、缓存与访问布局

### 6.1 两类 Shared 冲突

**Bank conflict**：文档给出 32 banks、4 B 宽度。一个 Warp 访问同 bank 的不同 word 时可能串行，同地址读可广播。对普通 32-bit 标量探针，可先用 `(byte_address/4)%32` 分析，但多字访问、矩阵 fragment、广播与写入规则仍需验证。

**Group conflict**：`ppu001` 有 2 个分组，各组连续跨度 128 B；间隔 256 B 的多请求可能集中到同组。即使单个 Warp 内没有 bank conflict，不同 Warp 或多段请求仍可能争抢同组。

可尝试 padding、XOR/swizzle、改变 Warp 分工和 Shared 读写顺序，但必须同时评估 producer 写、consumer 读和矩阵布局转换。AIU 自动 swizzle 也不意味着任意后续访问都无冲突。[HGGC 冲突说明](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=611#1511-避免线程共享内存冲突)、[优化指南 Shared 部分](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=832)。

### 6.2 L1、L2、LLC 与 HBM

`VREG/SREG → Shared与缓存层级 → L1(CU) → L2(CE) → LLC(跨CE) → HBM` 可用于理解作用域；Shared 是显式地址空间，不能把该表示理解为每次 load 必然串行穿过 Shared。

优化需要区分：CU 内 tile 复用、同 CE 内缓存复用、跨 CE 的 LLC 复用及 HBM 读取。小工作集反复 benchmark 可能主要测缓存；KV、权重和临时激活的复用距离也不同。L2/LLC 容量、映射和调度亲和性未实测前，不承诺“某个 tile 一定驻留某层”。

`hggcDeviceGetAttribute(..., hggcDevAttrL2CacheSize, ...)` 可查询文档公开的属性；其对应的共享域和量纲还需核对当前实现。不要把 L2 数值自动当成全设备最后一级缓存容量。[HGGC 内存层次](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=611)。

### 6.3 缓存策略与独立预取

普通 TIX load 的文档语义：`.ca` 缓存各级；`.cr` 绕过 L1；`.cg` 绕过 L1/L2、缓存 LLC；`.rt/.ba` 涉及全层 through/bypass；`.cs/.cv` 表达特定替换倾向。store 有 `.wb/.cg/.wt/.cs/.bl/.ba` 等选择。**这些是该指令族的语义/性能提示，应查看具体限定符，不按同名参数在其他后端的含义套用。**

cache policy 不替代内存一致性。修改前固定工作集、复用、对齐和地址分布；之后同时看各缓存请求/命中、后端流量与无 profiler 时间。

810E 的预取需要区分两件事：

- TIX 独立 `ppu.prefetch.global.L1` 被标注支持 `ppu001`，可作为待实测候选。
- load/AIU 的额外 `.level::prefetch_size`（128B/256B 到 LLC）属于 `ppu0015+`，不能用于 810E。

不能将“810E 没有后一种预取粒度提示”写成“完全没有 prefetch 指令”。[TIX 缓存策略](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=612#71-缓存操作符)、[独立 prefetch](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=612#ppu-prefetch)。

### 6.4 合并、宽访存与地址开销

优先让相邻 lane 访问相邻有效地址；检查真实首地址、行跨度、切片偏移和尾 mask，不能只看 tensor 的逻辑 contiguous 标志。`float4/int4` 提供宽类型表达，但实际指令宽度由对齐、别名和使用方式决定。

`__restrict__` 和 `__ldg` 等可表达真实的无别名/只读条件，不得通过错误声明换取编译。Paged KV、量化 metadata 和 gather 的地址生成也消耗 ALU：公共 page 基址复用、减少重复取模/除法需保证索引范围和负数语义正确。[优化指南：内存访问](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=832)。

## 7. Warp 通信、同步与原子

### 7.1 Warp32 通信

文档提供 shuffle、vote、match、activemask、redux，适合小范围归约、广播、相等 key 分组、掩码统计和路由。`membermask` 为 32-bit，对应 32 lanes。

必须证明每个参与线程按相同约定执行，数据来源 lane 活跃且属于参与集合。完整 Warp、尾 Warp、分支后的参与集合需分别验证；不将 `0xffffffff` 复制到实际只有少数有效 lane 的路径。

跨 Warp 通常需要 Shared 与块级同步；`__syncthreads()` 只能用于满足块内全员到达条件的位置。fence 表示排序，不等于所有线程到达，不等于所有异步搬运完成。[TIX Warp 级通信](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=612#83-warp-级通信)、[shuffle](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=612#ppu-shfl-sync)。

### 7.2 `ppu001` native 原子类型

下面是**官方优化指南列出的 native 支持表**，尚未在本机逐项执行；高层 API 暴露更多类型时，可能需要展开或仿真。

| 空间 | 操作 | 文档列出的 native 类型 |
| --- | --- | --- |
| Global | Add、Min、Max | U32/I32/U64/I64/F32/F64 |
| Global | And/Or/Xor、Exchange、CAS | B32/B64 |
| Global | Inc/Dec | U32/U64 |
| Shared | Add、Min、Max | U32/I32 |
| Shared | And/Or/Xor | B32 |
| Shared | Inc/Dec | U32 |
| Shared | Exchange、CAS | B32/B64；文档特别指出本代 Shared CAS 性能较差 |

不要将全局 native F16x2/BF16x2 原子归入本代；这是指南中列给 `ppu0015` 的新增内容。Shared F32 Add 的高层可用性也不等于 native 单指令支持。

避免大量线程竞争同一地址，能先做 Warp/Block 聚合时再发全局更新。本代全局原子还对 Warp 地址连续性及 128 B 对齐敏感，但文档举例中的比例不能当成所有 workload 的性能常数。

HGGC 支持显式 scope 的 `atomic/atomic_ref`。选择 relaxed/acquire/release 前明确计数、数据发布和 flag 协议；原子性不等于其他内存访问都已可见。指南另列 generic CAS 访问 Shared 的限制，应按地址空间显式表达并在目标 SDK 验证。[优化指南：原子操作](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=832)、[HGGC 原子接口](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=611)。

## 8. 运行时、互联与实例形态

### 8.1 Host copy、DMA、stream 与 Graph

HGGC 运行时提供异步执行、stream、Event、Graph 和内存管理接口。其可编译、可调用与实际并发收益分开验证：copy 是否走独立资源、copy/compute 是否重叠、多个 kernel 是否同时驻留，都需要当前机器证据。

主机传输考察 pinned、NUMA、PCIe 链路、批量大小、内存生命周期和依赖；Graph 用于评估重复 launch/CPU 开销，不保证改变 kernel 内部计算效率。统一内存、memory pool、cooperative launch 等通过当前设备属性查询后再使用，不能由 HGGC 有该 API 就确认全特性硬件支持。[HGGC 异步与运行时模型](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=611#23-异步编程模式)。

### 8.2 ICN、P2P 与多卡

ICN 是 810E 的片间互联。700 GB/s 为产品页面标称；服务器可能非全互联，设备编号相邻不等于链路近。TP/EP/PP 的卡组选择需结合具体拓扑、共享链路和 RDMA/PCIe 路径。

先通过 `ppu-smi` 的本版拓扑查询、P2P 工具确认实际连接，再用 `sailbandwidth` 评估单向/双向、读/写、并发、Host/Device 路径。PCCL 与 DeepEP 提供通信入口，但协议和环境变量按所用版本，不能复制其他集群的设备重排表。

来源：[PCCL 高性能实践](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=35&chapterId=862)、[sailbandwidth](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=35&chapterId=871)。

### 8.3 MIG、vGPU 与共享环境

官方提供 MIG 与 `ppu001` 的 SR-IOV/vGPU 文档。实例可能只暴露部分计算/显存，并共享某些 DMA 或其他资源；设备型号字符串不足以判断是否是整卡。先记录逻辑设备、UUID、可见资源、切分状态和其他负载。

文档中的 GI/CI、最大实例数和旧版本 Release Note 存在不同层次的计数，不在本知识库给出一个不带条件的“最大切成 N 份”。优化核验阶段只查询状态，不改变 MIG、复位、时钟或功耗配置。[MIG 指南](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=33&chapterId=686)、[ppu001 SR-IOV/vGPU](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=33&chapterId=690)。

## 9. 编译栈：如何拿到可核验的底层产物

### 9.1 HGGC、兼容层与实际 target

原生 SDK 使用 `hgcc` 编译 HGGC 源码（常见 `.hg`），通过 `hggc_*` 接口开发。早期 CUDA 兼容层还可能暴露 `nvcc`、`cuda*`、`nvcuda::wmma` 等名称。必须记录实际编译器路径、版本、头文件和链接库；兼容入口的存在不说明运行的是其他厂商的二进制。

**本机已验证**：`torch.cuda` 返回 `(major,minor)=(8,0)`，Triton target 为 `GPUTarget(backend='cuda', arch=80, warp_size=32)`，但 compiled metadata 的 `backend_name='ppu'`、device binary 为 HGBIN、最终 PASM 为 PPU 指令。不能从 `cuda/sm80` 的兼容标识认定是 NVIDIA SM80，也不能照搬其他 SM80 后端的原生支持判断。

本机 `hgcc --version` 和 `hgcc -V` 均报 unknown argument；`hgcc --help` 可用。兼容 `nvcc --version` 返回 release 13.0，`ppu-smi` 显示 HGGC 13.0；这两个值都不等于 SAIL SDK 发布号。两个 `VERSION.txt` 当前只有 detection magic，故没有据此填写 SDK 版本。

**官方明确：用 NVIDIA GPU CUDA SDK 编译的 device binary 不能直接在 PPU 上运行。** 依赖包要用适配版本或在目标工具链重编译，不能仅因 import/链接成功就确认 kernel 适配。[PPU 编程指南兼容说明](https://help.aliyun.com/zh/document_detail/2871803.html)。

### 9.2 原生编译与资源报告模板

以下为**官方文档中的参数组合，未在用户容器执行**。仅在确认目标版本支持时用于任务目录中的最小探针：

```bash
hgcc -arch=ppu_10 -O3 -lineinfo -res-usage \
  --keep --keep-dir=outputs/compiler probe.hg -o outputs/probe

hgcc -arch=ppu_10 --bc probe.hg
hgcc -arch=ppu_10 --opt-bc probe.hg

hgobjdump -l outputs/probe
hgobjdump -i=all outputs/probe
hgobjdump --isa outputs/probe
```

预先创建输出目录。`--bc/--opt-bc` 生成 LLVM bitcode，查看文本需要版本兼容的 LLVM 工具；不能拿任意版本 `llvm-dis/llc` 强行重编译。`hgbat` 可分析提取后的 HGBIN 的控制流和寄存器活跃区间，支持方式以本机 `--help` 为准。

区分三个层次：

1. 高层 API/源码写法。
2. **TIX 是抽象指令接口**，不是天然一对一的物理指令；`.ex` 尤其可能扩展成多条。
3. 最终 ISA/PASM 与资源分配，使用 HGCC 产物、`hgobjdump`、`hgbat` 确认。

不能只搜索到一条 TIX 名字就宣称原生指令已执行。[HGCC 工具链](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=625)、[Binary Utilities](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=630)。

### 9.3 Triton 缓存、IR 与特化归属

先确认本机 `triton-for-sail` 的版本、backend/target 和实际已选配置，再保存被 launch 的 compiled kernel 所暴露的 `asm`、metadata 和资源。不同安装版本的 key、dump 环境变量和 cache 结构可能不同；本文件不把天数专有的开关复制到 PPU。

需要缓存 IR 时，记录源代码摘要、signature、dtype、shape、host rank/strides、pointer offset、mask、消费者、warps/stages、编译选项和 cache key。不能按缓存目录里“最新文件”判断当前 kernel，也不能用另一个 autotune 配置的汇编解释测量结果。

**本机已验证产物入口**：Triton 3.6.0 / FlagTree `0.7.0+ppu.git47970467` 的已 launch kernel 暴露 `asm` keys：`source/ttir/ttgir/llir/hgbin/cubin`，本轮没有 `asm/ptx/sass` 文本 key。将 `kernel.asm["hgbin"]` 的 bytes 保存，再用 `hgobjdump --isa` 成功反汇编。`cubin` 是兼容命名，不能据其 key 名判断实际 ISA。

优先检查矩阵、AIU、异步 copy、swizzle、类型转换和 spill 的完整序列；API 候选 metadata 只能说明软件选择的一部分。[triton-for-sail 官方入口](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=46&chapterId=758)。具体自动触发规则尚待安装版本源码与探针核验。

## 10. Asight：证明路径执行与解释性能

### 10.1 工具各回答什么

| 工具 | 主要证据 | 不应混淆 |
| --- | --- | --- |
| `ppu-smi` / HGML | 设备、驱动、显存、拓扑、实例、温度/功耗等状态 | 整卡利用率不等于一个算子的指令利用率 |
| Asight Compute `acu` | 单 kernel 的管线、访存、资源、调度和停顿 | 采集存在不等于某个 metric 在本卡可用 |
| Asight Systems `asys` | Host/API/kernel/copy/通信的关联时间线 | 不用静态 async 指令代替动态重叠证据 |
| `hgobjdump/hgbat` | 指令、资源、控制流和活跃区间 | 证明生成，不单独证明执行频次或性能 |
| Event/项目 benchmark | 无 profiler 的正确 workload 耗时/吞吐 | 不使用 profiler replay 期间应用输出的平均时间作加速比 |

本平台分析器为 **Asight Compute/Systems**，不套用天数的 `ixkn-cli`。[Compute 快速入门](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=1&chapterId=717)、[PPU-SMI](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=636)。

### 10.2 最小采集与导出

以下是**文档支持、目标机未执行**的模板，参数和 section 先用当前工具查询：

```bash
acu --version
acu --list-sets
acu --list-sections
acu --query-metrics

acu --section ComputeWorkloadAnalysis \
  --section MemoryWorkloadAnalysis \
  --section LaunchStats \
  -k 'regex:target_kernel' -s 5 -c 1 \
  -o profile/candidate ./outputs/probe

acu --import profile/candidate.acurep --page raw --csv \
  > profile/candidate.raw.csv
```

skip/count 按程序实际 warmup 与匹配 launch 设定，不是固定采样规范。必要时增加 `InstructionStats`、`Occupancy`、`SchedulerStats`、`WarpStateStats`，不要为了“全面”每次采集全部指标。不同 section 使用重复 `--section`，不假设另一家工具的逗号语法。

**重要副作用与计时边界**：当前 CLI 文档中，`--kill` 默认 yes，达到采集次数可终止应用；不能直接套到仍需服务的进程。Replay 会改变时间与 cache 状态；文档的 `--cache-control none` 也并非“完全不刷缓存”，其口径仍涉及 L1/L2 刷新。记录 replay/cache/clock 配置并与基准一致解释，不为采集擅自锁频或改系统。

来源：[acu 命令行选项](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=1&chapterId=719)、[Compute 使用指南](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=1&chapterId=718)。

**本机工具与采集边界（2026-10-17）**：`acu --version` 为 `v2.1.0_20260416-3bb05b6`，Data version 15000；`--list-sections` 成功列出 InstructionStats、ComputeWorkloadAnalysis、LaunchStats、MemoryWorkloadAnalysis、Occupancy 等。实际运行 `acu --section InstructionStats -k regex:dot_probe -s 2 -c 1 --kill no -o ... python3 profile_driver.py` 返回 **101**，报 **`Device is not ready for profiling`** 并终止目标进程；导出的报告经 `acu --import ... --page raw --csv` 读取为 **`No kernel in report.`**

因此当前状态是“工具发现成功、目标采集失败”，本机没有有效动态计数器数据。没有尝试复位、杀其他进程、改权限或驱动配置；失败原因未定位，不能仅凭该报错认定硬件不支持 profiling。后续先按本机版本 FAQ 与环境管理规则排查，再采；本轮功能结论来自实际执行、完整对拍和匹配二进制反汇编，未扩写成动态利用率或加速比。

**失败原因的后续只读诊断**：官方 FAQ 将该错误的常见原因说明为 **PCM（性能数据采集资源）被其他 profiler 或后台监控占用**。当前 KMD `1.3.2` 低于 FAQ 中 GPM 临时禁用机制要求的 `1.4.0`，不能照抄新驱动的 GPM 开关。容器内 `ppu-smi` 未列出计算进程，进程列表未发现 acu/asys/监控进程；但这不排除宿主机或其他容器持有 PCM。容器未安装 `lsof`，`dmesg` 返回 `Operation not permitted`，因此尚未定位具体占用者。需要宿主机管理员通过只读设备句柄与驱动日志确认；不把“可能是监控占用”标为已确定根因，也不将容器无法读取日志误认为 acu 失败的直接原因。[官方 FAQ：Device is not ready for profiling](https://help.aliyun.com/zh/document_detail/2996868.html)。

### 10.3 哪些指标支持哪些结论

| 要核验的机制 | 编译/静态证据 | 动态证据方向 |
| --- | --- | --- |
| Tensor Cell | `tc01` MMA 与实际 PASM、dtype/layout | Tensor 管线指标、计算 workload、指令 mix |
| Packed 半精度 | packed FMA/ALU 与前后转换 | FP16/FALU 活跃、实际指令数；粗类别不唯一证明助记符 |
| AIU staging | AIU 与匹配的 swizzle load、完成等待 | 搬运/访存、资源、stall 改变；普通总流量不是 AIU 唯一指纹 |
| 合并或缓存策略 | load/store 宽度与 policy、真实地址 | L1/L2/LLC 请求和命中、HBM 路径、LSU 利用 |
| Shared 布局 | producer/consumer 的地址式、读写指令 | Shared 读写各自的 bank/group 冲突；计数不可用时用受控探针 |
| 多 stage/寄存器优化 | buffer 数、VREG/SREG、spill、wait 位置 | 理论/实际驻留、调度、Warp stall 与正式计时 |
| Host/Device 或多卡重叠 | 源码依赖与运行时调用 | Systems 时间线、受控并发与串行对照 |

文档示例可见的 metric 包括 `cu__inst_executed_pipe_tensor_fp16...`、`cu__inst_executed_pipe_tensor_tf32...`、`cu__inst_executed_pipe_sfu...`、`llc__transaction_hit_rate.pct` 等。**以当前 `--query-metrics` 为准**；利用率百分比、指令次数、吞吐和模型 FLOPs 不是同一单位，不能相互替代。[Compute 指标与分析章节](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=1&chapterId=718)。

### 10.4 Python 解析与归档

官方 `acu_report` 位于 SDK 的 `asight/extras/python`，提供 `load_report`、ranges/actions、metric 查询与取值接口。将报告解析为带单位的结构化数据，再做候选对比；保留原始 `.acurep`、stderr、版本、kernel filter 和 launch 归属。不要用字符串截取或错误类型读取把缺失 metric 变成 0。

结论分开记录：**接口存在 → 编译生成 → 动态观测 → 正确性通过 → 正式 benchmark 获益**。性能结论还要覆盖任务要求的 shape、尾块、布局和误差，不因专用指令出现就提前晋升候选。[报告解析 API](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=1&chapterId=721)。

```python
import json
import torch

result = {"torch_version": torch.__version__, "devices": []}
for i in range(torch.cuda.device_count()):
    p = torch.cuda.get_device_properties(i)
    item = {"logical_device": i, "properties_repr": str(p)}
    for name in ("name", "total_memory", "multi_processor_count", "warp_size",
                 "max_threads_per_multi_processor", "regs_per_multiprocessor",
                 "shared_memory_per_multiprocessor", "shared_memory_per_block",
                 "l2_cache_size", "async_engine_count"):
        item[name] = getattr(p, name, None)
    result["devices"].append(item)
print(json.dumps(result, ensure_ascii=False, indent=2))
```

这是查询模板，不是对目标环境 import、字段或 CUDA 命名兼容性的保证。关键资源以 HGGC API/头文件继续核验，尤其检查 `hggcDevAttrSharedMemPerBlock` 与 `hggcDevAttrSharedMemPerMultiprocessor`，以及 VREG 冲突口径。[HGGC 属性查询](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=611)、[PPU-SMI](https://developer.t-head.cn/docs_center/doc_detail/index.html?projectId=39&chapterId=636)。

| P2 | 2:4 sparse MMA | B 压缩与 metadata、支持 shape、误差与包含预处理的收益 |
| P2 | Host copy/Graph/P2P | pinned、依赖、实际 DMA 能力、捕获边界、拓扑及时间线 |

P0/P1/P2 为本文件的建议次序，不要求每次优化跑完整硬件套件。每个探针有超时、独立输入/输出和明确失败记录，不修改用户模型、任务比较器或系统配置。正确性通过后才采计数和正式时间。

## 12. 面向模型算子的使用顺序

以下为**优化推导**，必须通过当前 workload 证据筛选：

| 算子或问题 | 优先评估的硬件路径 | 常见抵消收益的成本 |
| --- | --- | --- |
| GEMM/MLP/MoE 专家 | 原生 tc01 + AIU + 配套 swizzle Shared，epilogue 融合 | 小 grid、片段重排、资源过大、权重准备 |
| Attention prefill | QK/PV 矩阵路径、KV staging、多 stage、融合 softmax | 两次矩阵间的精度转换、同步、累加器与 Shared 占用 |
| Attention decode | KV 的合并/缓存、page 地址复用、head/token 并行度 | 不规则 gather、mask 浪费、地址算术、split 合并 |
| RMSNorm/LayerNorm/softmax | Warp32 归约、Shared 跨 Warp、SFU、减少重复读写 | 短行利用不足、局部内存、过多跨 Warp 同步 |
| 量化/反量化 | Packed 算术/FMA、DP4A、字节排列与后续矩阵融合 | scale/zero point、pack/unpack、精度与对齐 |
| 路由/scatter/直方图 | Warp 分组、本地聚合、native 原子 | 热点竞争、Shared CAS、非连续全局原子 |
| 小 kernel/多请求 | 减少 launch、融合、Graph 与确实可用的并发 | 融合后资源增大、跨 stream 依赖、捕获限制 |

为每个候选写清：目标单元/路径、源代码触发条件、预期产物、正确性风险、资源代价和证伪条件。验证时用 **API/布局 → IR/TIX → PASM → 计数/时间线 → 无 profiler benchmark**，避免只调 tile 和 warps 而未检查是否用到高效单元。

## 13. 明确不直接采用的结论

- 不把 `ppu0015/tc02` 的原生 FP8、MXFP4、增强 AIU 或 LLC 预取粒度提示算到 810E。
- 不因 SDK 有 FP8/FP4 类型、转换或模型支持，就认定有相应原生矩阵吞吐。
- 不把 WMMA 逻辑 shape、`tc01.ex` 形状扩展与单条原生指令等同。
- 不把 256 KB/CU Shared 等同于单 block 可用量；不在 VREG 口径冲突时固定 occupancy 计算常数。
- 不把 TIX、LLVM intrinsic、头文件声明当作最终 PASM 或本机执行结果。
- 不把 Shared 自动 swizzle 当作任意 consumer 零冲突；不只看 Shared 写端指标。
- 不把 `prefetch` 支持一概写成有或没有；区分 L1 独立指令与另一代的 LLC 粒度提示。
- 不因异步 API、stages、stream 或 DMA 属性存在就宣称已经重叠。
- 不把 native 原子类型表外的高层 API 当作同样代价的硬件操作。
- 不把 2765 GB/s、700 GB/s 或产品性能宣传当成本机有效 kernel/通信带宽。
- 不把其他机器、其他 SDK 或其他厂商的细节继承为 810E 的支持结论。
