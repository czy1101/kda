# 天数智芯 BI-V150 使用与避坑知识库

## 先看这里：高频避坑清单

1. BI-V150 的 `torch.cuda.get_device_capability()` 返回 `(7, 1)`，这不是 NVIDIA SM 7.1，不能据此判断 Tensor Core、FP8、PDL 或 WGMMA 能力。
2. 显式 CUDA 风格 kernel 使用 CoreX `clang++ -x ivcore --cuda-gpu-arch=ivcore11`；本机 `nvcc` 包装器不能用于实际编译。
3. Triton kernel 先从 `num_warps=4`、`num_stages=1` 和较小 tile 起步；动态问题规模不要用 `static_range` 展开。
4. shared memory 单 block 上限按 128 KiB 规划，并同时检查 `n_regs`、`n_spills`；大 grid 下少量 spill 也可能造成 launch OOM。
5. FP8“可存储”不等于“适合 FP8 MMA”。已验证更稳的路径是 FP8 存储、load 后转 BF16，再走 `tl.dot`。
6. 64-lane、32-bit scalar shared-memory 探针显示：并发 word index 对 64 取余后应尽量不同；该规律不能直接外推到 BF16 向量写、SME 或完整 attention。
7. 隔离 Q buffer 零冲突不代表生产 kernel 更快。接入后必须同时复查 shared store/load conflict、寄存器、occupancy、正确性和普通计时。
8. Warp64 的 ballot 结果必须用 64-bit 类型保存；迁移 Warp32 算法时显式检查 shuffle width、参与 lanes 和归约范围。
9. `nv_mma_shared_layout`、NVIDIA WGMMA/TMA/PDL、Hopper mbarrier、`tle.gpu.wgmma`、`set_layout`、`warp_specialize` 和 `--maxnreg` 不要直接照搬；TLE 可用子集见第 7 节。
10. 环境中只有 `python3.12`；设置项目路径时使用 `PYTHONPATH=src:$PYTHONPATH`，不要覆盖 CoreX 原有路径。
11. 性能结论以无 profiler 的正式 workload 计时为准；ixKN duration 只用于解释硬件行为和筛选方向。

# 第一部分　硬件相关

本部分记录设备画像、硬件约束和可重复的 shared-memory / tensor-core 行为。涉及探针的数据只在其注明的访问宽度、线程布局和 shape 范围内成立。

## 1. 硬件快速结论

BI-V150 走 **CUDA 设备接口 + CoreX 运行时**，Triton target 是 `GPUTarget(backend='corex', arch=71, warp_size=64)`。对外像一张「假 SM 7.1」的 CUDA 卡，对内是 **ivcore11**：16 个 SM、warp=64、每 SM 共享内存 128 KiB、TCU 做 16×16 MMA。N 卡 Hopper 那套（WGMMA layout、TMA descriptor、PDL、`num_ctas>1`、按 SM 8.9 判断 FP8）都不能直接用。

| --- | --- | --- | --- |
| TCU 矩阵乘加 | `tl.dot(a,b,acc)` | 合法 dtype、矩阵 tile 和 operand 布局；所测半/单精度 K 粒度 16，INT8 为 32 | `ml_matrix_mad_*`，并完整对拍 |

### 4.2 SM（对写 kernel 有用的数字）

SM、torch 的 multiprocessor、ixkn 的 CU 是同一个东西。每卡 **16** 个。ixkn 字段名里的 `Per CU` 就是 per SM。

**Warp 和 NR**（2026-09-28）。执行单位仍是 warp，每组 **64** 线程（NVIDIA 是 32）。Triton `num_warps`、ixkn `Launched Warps` 都是这个。NR 是 ixkn 自己的名字，指 SM 里一块能同时留下 **8 个 warp** 的调度槽，对应 NVIDIA 上 SM 再拆成若干 warp scheduler / SMSP 那一层，不是另一套执行模型。共享内存和寄存器按整个 SM 分，不按 NR。

```text
每 SM 最多 8192 线程 = 128 个 warp
每个 NR 最多 8 个 warp → 每 SM 相当于 16 个 NR
占用率 = 该 NR 上活跃 warp / 8
       = 该 SM 上活跃 warp / 128
```

对照：某核 `Theoretical Active Warps Per CU = 32`、占用 25%：32 / 128 = 25%，平均每个 NR 留下 2 个 warp。写 kernel 按 warp 和 SM 想；看 ixkn Occupancy 再换成「每个 NR 最多 8 个 warp」。

| 项                               | 值                           | 备注                                                        |
| ------------------------------- | --------------------------- | --------------------------------------------------------- |
| `get_device_capability()`       | **(7, 1)**                  | 上报值。上报 (7,1) 不表示「Volta、没有 FP8」                            |
| Triton arch                     | `sm71` → ISA **`ivcore11`** | compiler：`capability==71 → ivcore11`；`80 → ivcore20`      |
| SM 数                            | **16**                      | `multi_processor_count`                                   |

| 每 SM 最大线程                       | 8192                        | `max_threads_per_multi_processor`；128 个 warp              |
| 每 NR 最大活跃 warp                  | 8                           | ixkn Occupancy 定义。每 SM 相当于 16 个 NR                        |
| 每 SM 共享内存                       | **131072 B（128 KiB）**       | `shared_memory_per_multiprocessor`。单个 block 上限同样是 128 KiB |
| 每 SM 向量寄存器                      | 262144 × 32-bit             | `regs_per_multiprocessor`；约 1 MiB。按线程再分，见下文               |
| 默认 `num_warps`                  | 4                           | CoreX Triton 默认；4 warp × 64 = **256 线程 / block**          |

| 硬件 named barrier / `setmaxnreg` | **没有**                      | ivcore11 的 warp specialize 用共享内存软件 barrier                |

**共享内存**（2026-09-28）。每个 SM 私有 128 KiB，SM 之间不共用。这块按 block 切给当前驻留在该 SM 上的 block：block 内线程共用分到的那一段，block 结束就释放。一个 block 可以拿满 128 KiB，拿满后该 SM 只能留这一个 block。

```text
shared 容量给出的驻留 block 上界 = floor(131072 / 每 block 共享内存字节数)
```

对照：6144 B/block 时 `floor(131072 / 6144) = 21`，与 ixkn `Block Limit Shared Mem Per CU = 21` 一致。静态和动态共享内存加在一起算进这个额度。

**标量寄存器和向量寄存器**（2026-09-28）。ixkn 的 Launch Statistics 分成两池，单位不同：

| ixkn 项 | 单位 | 用途 | 占用上限字段（CU = SM） |
| --- | --- | --- | --- |
| Scalar Register | Registers/Warp | 一个 warp 共用。循环下标、共享基地址这类整组线程相同的值，走 Single-Lane 指令 | `Block Limit SRF Per CU` |
| Vector Register | Registers/Thread | 每个线程一份。各线程不同的 Q/K/V 元素和累加器，走 Multi-Lane 指令 | `Block Limit VRF Per CU` |

`regs_per_multiprocessor = 262144` 是**每个 SM 的向量寄存器池**。已测编译路径上，每线程分到 256 时会出现 local memory / spill（FP8 MMA：`n_regs=256`、`n_spills=295`）。本文把 256 记为**已观察到的高压分配点**，不写成“所有 kernel 的通用硬件硬上限”。ixkn 的 `Vector Register N Registers/Thread` 和 Triton 的 `n_regs` 都是该次编译实际分到的个数。标量寄存器另池，不占这 262144；本机没有单独报出 SRF 总容量。

向量寄存器换算驻留：

```text
满驻留时每线程预算 = 262144 / 8192 = 32
VRF 容量给出的粗略驻留 block 上界 = floor(262144 / (每线程向量寄存器 × block 线程数))
```

对照：112 regs/thread、block 512 线程时，`floor(262144 / 57344) = 4`，与 ixkn `Block Limit VRF Per CU = 4` 一致。

换算占用时不要用 NVIDIA 习惯：

```text
block 线程数 = num_warps × 64
local memory ≈ n_spills × 4 × (num_warps × 64)  字节/block
```

MSA FP8 MMA 爆显存就是按这个算的：`num_warps=4` → 256 线程，295 spill × 4 B × 256 × 131072 block ≈ 37–40 GiB，超过 32 GiB。


**寄存器在算子中的用途与调优**：VRF 保存每线程数据、矩阵 accumulator 和频繁复用的中间值，减少设备内存往返；SRF 承载 warp 一致的基址、行跨度和循环变量。控制 tile、循环展开与 staging 引入的寄存器压力，并缩短临时值生命周期。满线程驻留时每线程平均预算只有 32 个向量寄存器，大 accumulator tile 往往需要用并发换复用。

**统一地址计算**：page 基址、行跨度尽量在同一组线程间复用。不规则逐元素 page 查表、除法和取模会增加指令，布局重排要把地址计算成本一起计入。local memory 可能增加设备内存流量，但是否成为瓶颈要看动态 local load/store，不能仅根据静态分配断言。

上述容量除法只给上界；实际驻留还受 VRF 分配粒度、SRF、shared、线程及 block 上限限制。具体例子：本节后面的压力实验中，65 registers/thread、256 threads/block 的 Runtime 结果为 12 blocks/SM，不能用简单相除得到的 15 替代。

##### 统一值复用与标量化的实测边界

**已验证统一值复用，但不保证自动标量化**：`scale=tl.load(S+tl.program_id(0))` 后广播到当前 program，与 `scale=tl.load(S+i)` 的逐元素版本相比，所测 kernel 中 scale 的普通数据 load 从 4 个静态位置减为 1 个，VRF 从 13 降到 11/thread，均 shared=0。

测试为 65536 个 FP32 元素、BLOCK=1024、4 warps，`x=1`、`S=arange(N)*0.001`，分别按 program 或按元素取 scale，两个结果均与各自参考完全相等。广播版本的 scale 实际仍通过 `ml_lsa_load_dword` 读入向量寄存器，**不能从“所有线程相同”直接推断该 load 已走 SRF/Single-Lane 路径**。

编写代码时将同一 program/warp 的公共 scale、page 基址、行跨度放在统一表达式中复用；scalarization 是否发生仍看指令与寄存器统计。这里只验证复用和资源差别，没有测端到端提速。（2026-10-15）

#### Warp64 通信语义与 Warp32 子组兼容性

运行时报告 `warpSize=64`；256-thread block 包含 4 个 Warp64，lane 编号每 64 个线程重新从 0 开始。以下结果均通过逐元素或 CPU 参考校验。

完整 Warp64 shuffle：

| 操作 | 错误元素数 | 结果 |
|---|---:|---|
| `__shfl_xor(value, 1, 64)` | 0 | PASS |
| `__shfl_xor(value, 32, 64)` | 0 | PASS |
| `__shfl(value, 0, 64)` | 0 | PASS |
| `__shfl_xor(value, 1, 32)` | 0 | PASS |

跨低、高 32 lanes 的边界行为为：lane 31 XOR 32 得到 lane 63，lane 32 得到 lane 0，lane 63 得到 lane 31。由此确认 CUDA 风格 `__shfl` / `__shfl_xor` 支持完整 Warp64 数据交换；设置 `width=32` 时，一个 Warp64 可形成两个互不串扰的 32-lane shuffle 子组。

基于 shuffle XOR 树的软件归约：

| 范围 | 操作 | 预期/实测 |
|---|---|---:|
| Warp64 | Sum，6 轮 | 2016 / 2016 |
| Warp64 | Max，6 轮 | 63 / 63 |
| 低 32 lanes | Sum，5 轮 | 496 / 496 |
| 高 32 lanes | Sum，5 轮 | 1520 / 1520 |

256 个线程全部正确，4 个 warp 之间未观察到数据串扰。这证明全 Warp64 和两个 Warp32 子组的软件归约语义可用，但不能据此确认存在专用硬件 reduce 指令。

完整 Warp64 `__ballot()` 返回 64-bit mask：

| 条件 | 掩码 |
|---|---|
| 偶数 lane | `0x5555555555555555` |
| lane 32～63 | `0xffffffff00000000` |
| 仅 lane 63 | `0x8000000000000000` |

迁移 NVIDIA Warp32 算法时：

- 不要把 ballot 结果保存为 32-bit `unsigned int`，否则高 32 lanes 会被截断。
- 需要保留 Warp32 逻辑时，可显式使用 `width=32` 构造两个子组，但必须重新检查索引、归约范围和参与线程。
- 已测试低 32 lanes 的 `_sync` shuffle/ballot 可以工作；完整 Warp64 的 `_sync` 参与 mask 语义仍未验证，不能把 `0xffffffffu` 当成完整 Warp64 mask。
- 接口结果证明语义正确，不代表已经确认每种操作对应的物理机器指令。

Shuffle 微基准使用 512 blocks、256 threads/block、128 轮具有数据依赖的 shuffle 和整数运算，并使用 CUDA Graph 计时：

| 访问模式 | WIDTH=32 | WIDTH=64 | 观察 |
|---|---:|---:|---|
| 交替 XOR 1 / 远距离 XOR（16 或 32） | 25.596933 μs | 21.327318 μs | WIDTH=64 快约 16.7%，但远距离掩码不同 |
| 固定 XOR 1 | 17.895602 μs | 18.432538 μs | WIDTH=32 快约 2.9% |

性能差异随 width 和访问模式变化，现有微基准不能推出“Warp64 单条 shuffle 更快/更慢”。工程上应先选择语义正确的子组宽度，再在真实算子和正式 shape 上决定性能。

##### Warp64 在行级算子中的使用

**有什么用：**

- 一个 warp 内可以用 shuffle 交换寄存器数据，完成 sum、max 等归约，减少 shared memory 往返。
- softmax、RMSNorm、LayerNorm、top-k 等行级算子可以按 64 lanes 分配数据，再进行组内协作。
- `ballot` 可将 64 个线程的条件压缩成 **64-bit mask**，用于筛选、计数和路由。
- shuffle 指定 `width=32` 时，可将一个 warp 分成两个独立子组，处理较短的行或两个小任务。

线程配置换算：

| `num_warps` | block 线程数 |
| --- | ---: |
| 1 | 64 |
| 2 | 128 |
| 4 | 256 |
| 8 | 512 |

归约范围、lane 编号和 ballot 类型都应按实际参与线程设计。对短行增加 warp 数可能扩大同步和数据交换开销，应按每行元素数选择。

**执行掩码：**本机汇编使用 `tmsk` 和相关保存/恢复指令管理 lane 的执行条件。对不等长序列、尾块与稀疏任务，应尽量让同一个 Warp64 的线程具有相近工作量。能将相似长度、相似稀疏度的任务放在一起时，可减少无效 lane 和路径分化。

##### 同一 Kernel 的 Runtime 与 ixKN 交叉验证（R4）

为验证寄存器字段和 occupancy 口径，固定 BI-V150 OAM、ivcore11、CoreX 4.4.0、grid=512、block=256、shared memory=0，仅改变每线程计算/寄存器压力。三组均通过正确性校验；性能使用无 profiler CUDA Graph，资源和 occupancy 使用 ixKN。

| 指标 | COUNT=32 | COUNT=64 | COUNT=128 |
|---|---:|---:|---:|
| Runtime `numRegs` | 34 | 66 | 130 |
| ixKN Vector Registers/Thread | 34 | 66 | 130 |
| ixKN Scalar Registers/Warp | 18 | 18 | 18 |
| Local Memory/Thread | 0 B | 0 B | 0 B |
| Runtime Blocks/SM | 28 | 12 | 4 |
| ixKN VRF Block Limit | 28 | 12 | 4 |
| Theoretical Occupancy | 87.50% | 37.50% | 12.50% |
| Achieved Occupancy | 65.72% | 33.95% | 12.21% |
| CUDA Graph 平均时间 | 11.995 μs | 22.517 μs | 46.482 μs |
| Executed Instructions | 1,277,952 | 2,457,600 | 4,816,896 |
| FP32 ALU Instructions | 1,179,648 | 2,359,296 | 4,718,592 |

由同一批 kernel 可确认：

1. Runtime `numRegs` 与 ixKN Vector Registers/Thread 完全一致，可以在这条编译/运行路径上视为同一每线程向量寄存器分配量的两种报告口径。
2. Scalar Registers/Warp 始终为 18，与 Vector Registers/Thread 独立统计，验证了 SRF 与 VRF 不能合并计算。
3. Runtime Blocks/SM 与 ixKN VRF Block Limit 完全一致；三组理论 occupancy 都由 VRF 限制。
4. Achieved Occupancy 低于理论上限：分别为理论值的约 75.1%、90.5% 和 97.7%。资源模型给出上限，不保证运行时一定填满。
5. COUNT=128 时，grid=512、16 SM、4 blocks/SM，正好对应每 SM 32 个 block 的总波次数为 8 个完整 wave；其 achieved occupancy 12.21% 已接近 12.50% 理论上限。
6. 三组均无 local-memory 分配，因此本组只验证“寄存器增加→VRF 驻留上限下降”，没有验证动态 spill。
7. FP32 ALU 和总指令数随 COUNT 近似成比例增加，而 Global Memory 指令保持不变。

性能解释必须保持控制变量边界：COUNT 同时提高了计算量和寄存器压力，因此 11.995→22.517→46.482 μs 的增长不能单独归因于 occupancy 下降。若要量化 occupancy 的独立影响，需要构造计算指令数相近、只改变寄存器生命周期或分配量的单变量实验。

R4 与前一组寄存器压力实验使用不同 kernel，不能直接比较相同 COUNT 下的寄存器数。前一组 COUNT=128 曾报告 256 registers/thread 和 4 B local/thread；R4 COUNT=128 为 130 registers/thread、0 B local/thread。两者共同说明资源分配取决于具体代码生成，不是 COUNT 参数本身决定。前一组仅有 `localSizeBytes=4` 的静态分配证据，**没有**闭合的动态 spill load/store 流量结论，故不据此推断 spill 是否成为瓶颈。

工程含义：

- 增大寄存器 tile、展开循环或长期保存 accumulator 会降低理论并发。
- 同一 R4 kernel 已验证 Runtime `numRegs` 与 ixKN Vector Registers/Thread 完全一致。换算子时不要默认三者永远相等，以该算子实际 `n_regs` / ixKN 为准。
- BI-V150 还单独报告 Scalar Registers/Warp，不能把标量和向量寄存器混成一个池。
- Runtime resident blocks 与 R4 的 ixKN VRF Block Limit 一致，但都只是理论资源上限；achieved occupancy 仍可能更低。local-memory 静态分配也不等于实际 spill 流量或必然性能下降。
- 常量循环即使有展开提示，编译器也可能选择不完全展开；应以实际资源和指令结果为准。

### 4.3 TCU

Triton 把 `tl.dot` 降到 **Iluvatar TCU v1**（compiler 注释写成 Volta-style MMA）。本机 lowering 只认 16×16 形状，走这些 LLVM intrinsic：

| 输入 | 累加 | intrinsic |
| --- | --- | --- |
| f16 | f32 | `llvm.bi.matrix.mad.f32x4.f16x4` |
| bf16 | f32 | `llvm.bi.matrix.mad.f32x4.bf16x4` |
| f32 | f32 | `llvm.bi.matrix.mad.f32x4.f32x4` |
| i8 | i32 | `llvm.bi.matrix.mad.i32x4.i8x8` |

编译器的最小 dot 形状与 TCU lowering 约束：

- 8-bit：`K >= 32`；tile K=16 会报 `Input shapes should have M >= 1, N >= 1 and K >= 32`。
- 其它：`K >= 16`。
- 暂不支持 batched TCU lowering。
- **FP8 不是 TCU 原生 operand**。compiler 写明 ivcore11 是 **software FP8**；`tl.dot` 小核可以过，大核把 Q 量化成 `float8e4nv` 做 MMA 会把寄存器顶满并 spill。

允许的 `tl.dot` 输入精度：`tf32`（默认）、`tf32x3`、`ieee`、`bf16x3`、`bf16x6`。


#### TCU 机器指令、用途与四精度正确性复核

**已验证**；环境与计量口径见本章前文。

**是什么：**专门执行矩阵乘加的计算单元。Triton 使用 `tl.dot` 调用，矩阵操作数分配给线程参与计算，累加结果保存在寄存器中。

2026-10-15 实测以下路径均通过正确性校验，并生成对应矩阵机器指令：

| 输入精度 | 累加精度 | 实测矩阵指令 | 主要用途 |
| --- | --- | --- | --- |
| FP16 | FP32 | `ml_matrix_mad_f32_f16_m16n16k16` | 半精度 GEMM、Attention、MLP |
| BF16 | FP32 | `ml_matrix_mad_f32_bf16_m16n16k16` | BF16 模型计算、较大动态范围的中间结果 |
| FP32 | FP32 | `ml_matrix_mad_f32_f32_m16n16k16` | 需要 FP32 输入精度的矩阵计算 |
| INT8 | INT32 | `ml_matrix_mad_i32_i8_m16n16k32` | 量化矩阵计算，后续融合 scale、bias、激活 |

这里的 `m16n16k16`、`m16n16k32` 表示所测指令的矩阵形状。FP16/BF16/FP32 的 K 分块至少按 16 元素组织，INT8 至少按 32 元素组织；程序 tile 可以由多个指令片段组成。

**怎么用：**

- 矩阵计算尽量组织成规则的二维 tile，使用 TCU 完成主要乘加。
- FP16/BF16 输入配 FP32 累加，可兼顾数据量与累加精度。
- INT8 路径显式使用 INT32 累加和 `out_dtype=tl.int32`，量化 scale 与输出转换尽量在相邻计算中融合。
- tile 增大会增加 operand 和 accumulator 寄存器占用，需要同时检查寄存器、shared memory 和并发 block 数。

2026-10-15 的 `512×512×512` GEMM、tile `32×32×32`、4 warps、1 stage 的上述四种精度全部通过。FP32 输入使用 `input_precision="ieee"`；浮点输出与 FP32 参考按 `atol=rtol=0.025` 校验，实测最大绝对误差 FP16 1.7882e-6、BF16 7.1526e-7、FP32 0。INT8 输入为 `[-3,3]` 整数，完整输出与 CPU INT32 矩阵参考逐元素一致。矩阵 tile 的其他配置需要独立验证正确性。（2026-10-15）

| Local Memory / Thread | 0 | 0 | 0 |

这些计数确认：

1. FP32、FP16、BF16 都实际执行 Matrix 指令，不是普通 ALU 模拟的纯软件矩阵乘。
2. 三者 Matrix 指令数相同，不代表单条指令成本或实际吞吐相同。
3. FP32 的 SME 指令数是 FP16/BF16 的两倍，shared-memory 指令约为 1.75 倍，每 block shared memory 也是两倍，向量寄存器占用更高。
4. 当前三种路径均无 local memory 分配。
5. `TCU Efficiency` 是 ixKN 内部指标；在公式未知时，不能跨精度直接解释成“达到各自理论峰值的百分比”。

为降低短 kernel 计时波动，使用 CUDA Graph 做稳定测试：编译并预热 20 次；每张 Graph 捕获 20 次 GEMM；Graph replay 预热 10 次；正式 replay 100 次，共 2,000 次 GEMM；用 CUDA Event 测整个 replay 序列后除以执行次数。三种精度分别正序、逆序测试：

| 精度 | 正序时间 | 逆序时间 | 平均时间 | 有效吞吐 |
|---|---:|---:|---:|---:|
| FP32 | 155.067 μs | 154.435 μs | 154.751 μs | 13.88 TFLOPS |
| FP16 | 67.130 μs | 67.255 μs | 67.193 μs | 31.96 TFLOPS |
| BF16 | 67.261 μs | 67.014 μs | 67.138 μs | 31.99 TFLOPS |

适用结论：

- 在这组固定 shape 和 tile 下，FP16/BF16 有效吞吐约为 FP32 的 2.3 倍。
- FP16 与 BF16 性能基本一致，当前差异没有实际意义；应按模型 dtype、动态范围和误差要求选择。
- 表中 TFLOPS 是 `2×M×N×K / 时间` 得到的固定工作负载有效吞吐，不是官方理论峰值，也不是全 shape 可达到的最高值。
- 半精度优势可能同时来自矩阵执行、数据宽度、SME/shared-memory 数据准备和资源占用，现有数据不能拆出每部分的独立贡献。
- 该倍率不能直接推广到 Attention、MoE 或其他 shape；正式优化仍需重新搜索 tile、warp 和 stage。
- INT8 已验证特定 tile 的完整 GEMM 与 Matrix 指令路径，但当前约 6.81 TOPS 不是吞吐上限；FP8 仍没有原生矩阵加速证据。


#### INT8×INT8→INT32 TCU 正确性、Tile 边界与吞吐实测

CoreX Triton 的 INT8 `tl.dot` 在使用 INT32 累加器时需要显式声明输出类型：

```python
acc = tl.full((BM, BN), 0, tl.int32)
acc = tl.dot(a, b, acc, out_dtype=tl.int32)
```

省略 `out_dtype=tl.int32` 会触发 accumulator 类型与返回类型不一致的编译断言；这是当前编程接口/编译器语义要求，不是硬件不支持 INT8。

正确性证据：

- 单次 `32×32` INT8 矩阵乘、INT32 输出：无显式 accumulator 和零初始化 INT32 accumulator 两种写法均最大误差 0、错误元素 0。
- 固定 `M=N=32, BK=32`，用 `while` 循环遍历 K：`K=32/64/128/256` 分别执行 1/2/4/8 次 dot，全部最大误差 0。这证明当前路径的 INT32 accumulator 至少可正确连续累加 8 个 K tile。
- 完整 `1024×1024×1024` GEMM 在 `BM=32, BN=32, BK=32`、`num_warps=4`、`num_stages=1` 下通过逐元素校验，最大误差 0。

Tile 正确性存在重要边界：

| Tile `(BM, BN, BK)` | 正确性 | 最大误差 | 初测时间 |
|---|---|---:|---:|
| `(32,64,32)` | FAIL | 1373 | ≈192.25 μs |
| `(32,32,32)` | PASS | 0 | ≈315.24 μs |

失败配置中有 1,047,130 / 1,048,576 个元素错误；结果既不等于完整 GEMM，也不等于只执行第一个 K tile；把循环显式改成 `while` 仍错误。因此：

- 当前 CoreX 4.4.0 的 INT8 GEMM 正确性会受 tile 配置影响，每个候选必须先完整对拍，再进入性能比较。
- 不能因为 `(32,64,32)` 失败就宣称硬件不支持 BN=64、所有 INT8 BN=64 都错误或 TCU 硬件有缺陷。本知识库只闭合到「该 tile 在当前编译路径上数值错误」；不把根因写成已定位。
- 错误但更快的候选没有性能意义，不能作为基线或优化结果。

对正确的 `(32,32,32)` 配置使用 CUDA Graph 稳定计时，三次结果为 315.239、315.246、315.237 μs，平均约 315.241 μs；按 `2×M×N×K / 时间` 计算，有效吞吐约 6.8122 TOPS。该数字只代表此 kernel、shape 和 tile，不是 INT8 理论峰值。

ixKN 对正确配置的证据：

| 指标 | 实测 |
|---|---:|
| Multi-Lane Matrix Instructions | 131,072 |
| TCU Efficiency | 1.3024% |
| Multi-Lane SME Memory Instructions | 0 |
| Multi-Lane Shared Memory Instructions | 3,145,728 |
| Multi-Lane Global Memory Instructions | 278,528 |
| Multi-Lane ALU Integer Instructions | 4,030,464 |
| BFU Instructions | 3,899,392 |
| Vector Registers / Thread | 30 |
| Dynamic Shared Memory / Block | 2,048 B |
| Local Memory / Thread | 0 B |

`Multi-Lane Matrix Instructions > 0` 证明正确的大 GEMM 确实执行了 Matrix/TCU 路径。但 TCU Efficiency 仅 1.3024%，同时整数 ALU、BFU 和 shared-memory 指令很多，说明**当前实现未证明已充分利用 INT8 矩阵管线**。BFU utilization 96.75% 与 integer compute pipeline utilization 100% 只作现象记录，**不**单独写成唯一瓶颈结论。

阶段性结论：INT8×INT8→INT32 `tl.dot`、多 K tile INT32 累加和完整 1024³ GEMM 均已在特定配置上验证；本知识库记录的稳定有效吞吐约 **6.81 TOPS**。不宣称这是吞吐上限，也不记录未验证的更优 tile。

**是什么：**`input_precision` 是编译器选择计算路径的入口，同名精度选项在本机不一定对应不同硬件模式。

本次 `256³` FP32 GEMM、tile `32³`、4 warps、1 stage，同一输入的结果如下：

| 模式 | 实际矩阵指令类型 | 寄存器/线程 | shared/block | 相对 FP32 参考的最大绝对误差 |

#### 矩阵转置布局与操作数准备

**已验证**。

**是什么：**TCU 的计算形状相同，A/B 的行列存储方式仍会改变输入准备。

本次 BF16 `256³` GEMM 的 `A×B`、`A×Bᵀ`、`Aᵀ×B`、`Aᵀ×Bᵀ` 都通过校验，全部使用 BF16 matrix mad。B 按转置方式读取时，每线程寄存器从 16 增至 19；四种 shared 均为 4 KiB。

**怎么用：**线性层权重、Attention 的 K 和 MoE 权重应连同 consumer 一起选择布局。把运行时转置或重排移动到可复用的预处理阶段，是否值得，取决于后续消费次数与准备成本；不能只比较转置前后的数学 shape。

四组均为 tile `32³`、4 warps、1 stage、FP32 累加与输出；Aᵀ/Bᵀ 表示通过地址步长读取原始数据的转置，不是预先物化转置张量。无 profiler 中位时间约 7.09–7.14 µs，不将微小差值解释为某布局必然更快。（2026-10-15）

### 4.4 FP8 到底有没有

**有存储、有转换、有小核 `tl.dot`；没有可在 bench 规模安全使用的 FP8 MMA。**

| 能力 | 状态 |
| --- | --- |
| `torch.float8_e4m3fn` 存储 / `.to()` 转换 | 通过。fp16↔e4m3 最大误差约 0.06 |
| Triton `tl.float8e4nv` `tl.dot` 32×32 | 通过，和 `a8.float() @ b8.float()` 对得上 |
| compiler `supported_fp8_dtypes` | `fp8e5` + **sm71 额外打开 `fp8e4nv`** |
| `fp8e4b15` | **不支持**（NVIDIA PTX 软件格式） |
| N 卡式 `q.to(float8e4nv)` + FP8 MMA | 小 shape 能对拍；bench 规模 `n_regs=256` 顶满、`n_spills=295`，launch OOM |
| 实际适配路径 | KV **按 FP8 存**，load 后 dequant 到 bf16/fp16 再 `tl.dot` |

不要用 `get_device_capability() >= (8, 9)` 判断天数卡有没有 FP8。那是 NVIDIA Ada/Hopper Tensor Core 门槛。天数卡按 `hasattr(torch, "float8_e4m3fn")` 打开存储路径即可。

#### FP8 小核与显式解码的实际矩阵指令

**已验证**。

FP8 E4M3 可以用于压缩存储，载入后转换成 FP16/BF16 计算。

本次直接给 `tl.dot` 输入 FP8 的 `32×32×32` 小核通过校验，但最终生成的是 **FP16 矩阵指令**。显式 FP8→BF16 的 `512³` GEMM 生成 **BF16 矩阵指令**，也通过校验。

**用途：**压缩权重或 KV cache 的存储容量及读取数据量。选择 FP8 时，需要把反量化、布局转换、寄存器和 scale 的成本一起计入；不能按 FP8 数据类型估算矩阵算力。

直接 FP8 小核 `n_regs=38`、shared 1024 B、`n_spills=0`；显式解码 BF16 的 `512³` GEMM 使用 tile `32³`、4 warps、1 stage，`n_regs=27`、shared 1024 B、`n_spills=0`。前者输出与量化后输入的 FP32 参考一致，后者最大绝对误差 0。只确认所测路径是 FP16/BF16 matrix mad，不外推为芯片完全不能处理 FP8。（2026-10-15）

#### FP8 E4M3 存储与 BF16 解码成本

在 `N=4,194,304`、`BLOCK=1024` 且所有地址合法的条件下，FP8 E4M3 load 后转换为 BF16，可相对已存储的 FP8 数据做到最大误差 0、错误元素 0。该正确性只证明“读取已量化 FP8 并解码”为真，不表示原始 FP16→FP8 量化没有误差。

当前 CoreX 4.4.0 对 FP8 masked load 有兼容性边界：

```python
# 可能因整数 other 无法隐式转为 FP8 而编译失败
x = tl.load(ptr + offsets, mask=mask, other=0)
```

若能静态保证所有地址合法，无 mask load 可以正常读取并转换；但不能为了绕过该限制而对可能越界的数据取消 mask。需要 masked load 时，应显式使用后端可接受的同类型 `other`，或改变边界处理方式，并重新做编译与正确性验证。

CUDA Graph 受控对照：

| 路径 | 输入 | 输出 | 逻辑流量 | 平均时间 | 正确性 |
|---|---:|---:|---:|---:|---|
| BF16 Copy | 8 MiB | 8 MiB | 16 MiB | 14.132 μs | PASS |
| FP8→BF16 | 4 MiB | 8 MiB | 12 MiB | 17.804 μs | PASS |

FP8 输入容量减半、总逻辑流量少 25%，但独立解码仍慢约 26%。ixKN 对照：

| 指标 | BF16 Copy | FP8→BF16 |
|---|---:|---:|
| Executed Instructions | 589,824 | 1,376,256 |
| Multi-Lane ALU Instructions | 278,528 | 851,968 |
| Integer ALU Instructions | 278,528 | 786,432 |
| Single Float ALU Instructions | 0 | 65,536 |
| Global Memory Instructions | 65,536 | 65,536 |
| Shared Memory Instructions | 0 | 49,152 |
| Vector Registers / Thread | 6 | 10 |
| Dynamic Shared Memory / Block | 0 B | 1,024 B |
| Matrix / SME Instructions | 0 / 0 | 0 / 0 |

FP8 解码的动态指令约为 2.33 倍，Multi-Lane ALU 约为 3.06 倍，整数 ALU 约为 2.82 倍，并新增 shared-memory 访问和资源占用。说明当前编译路径的格式转换/数据整理开销可以抵消输入带宽节省；汇总计数仍不足以把全部额外延迟唯一归因于某类指令。

#### FP8 存储融合 BF16 GEMM

受控比较两条路径：

- BF16 存储 → BF16 `tl.dot` → FP32 accumulator/output。
- FP8 存储 → kernel 内转 BF16 → 同样的 BF16 `tl.dot` → FP32 accumulator/output。

两组使用 `M=N=K=1024`、`BM=32, BN=64, BK=32`、`num_warps=4`、`num_stages=1`。BF16 对照输入由同一份 FP8 数据预先解码得到，因此两条路径使用完全相同的量化后数值，输出最大/平均绝对误差均为 0。

| 指标 | BF16 GEMM | FP8 存储+BF16 GEMM |
|---|---:|---:|
| 输入总量 | 4 MiB | 2 MiB |
| 平均时间 | 170.962 μs | 267.919 μs |
| 有效吞吐 | ≈12.56 TFLOPS | ≈8.02 TFLOPS |
| Matrix Instructions | 262,144 | 262,144 |
| Executed Instructions | 3,948,544 | 13,910,016 |
| Multi-Lane ALU Instructions | 1,564,672 | 10,698,752 |
| Integer ALU Instructions | 1,302,528 | 8,863,744 |
| Single Float ALU Instructions | 262,144 | 1,835,008 |
| Global Memory Instructions | 409,600 | 212,992 |
| Shared Memory Instructions | 1,572,864 | 2,359,296 |
| SME Memory Instructions | 0 | 0 |
| Vector Registers / Thread | 27 | 42 |
| Dynamic Shared Memory / Block | 6,144 B | 2,048 B |
| Local Memory / Thread | 0 B | 0 B |
| TCU Efficiency | 11.5543% | 7.2609% |

FP8 路径把 Global Memory 指令减少约 48%，但总动态指令增至约 3.52 倍、Multi-Lane ALU 增至约 6.84 倍、整数 ALU 增至约 6.81 倍、shared-memory 指令增加 50%，寄存器从 27 增至 42。最终执行时间增加约 56.7%。

这组结果说明：

1. FP8 E4M3 可作为存储格式，能够在 kernel 内正确转成 BF16 并进入 BF16 Matrix 路径。
2. 两条路径 Matrix 指令数相同，因此该 FP8 方案是“压缩存储+软件解码+BF16 计算”，不是原生 FP8 MMA。
3. 输入减半不保证加速；若解码、布局转换、shared-memory 和寄存器成本更高，FP8 会比 BF16 更慢。
4. 该结论只适用于当前 shape、tile、设备和编译路径；更换 tile/warp/stage 后仍需重测。
5. 独立解码与融合 GEMM 的性能结论均以无 profiler CUDA Graph 为准。两者的 ixKN Duration 排序可能受 replay 影响，只用于解释指令与资源差异。
6. 当前仍没有 BI-V150 原生高吞吐 FP8 Matrix 指令的充分证据，但也不能据此写成“硬件不支持 FP8”。

### 4.5 和「看起来像 NVIDIA」的差异

天数软件栈大量复用 CUDA 名字（`nvcc`、`cubin`、`libcuda.so.1`、`torch.cuda`），但：

| NVIDIA 习惯 | BI-V150 实际 |
| --- | --- |
| SM 80/90/100 | 上报 (7,1)，ISA 是 `ivcore11` |
| warp=32 | warp=64 |
| Hopper WGMMA + TMA | TLE **拒绝** `nv_mma_shared_layout=True` |
| `maxnreg` 限制每线程寄存器 | compiler 映射成 `iluvatar-num-vgpr`；**不要照抄 H100 的 168/128** |
| `num_threads = num_warps * 32` | `triton.language.extra.corex.num_threads` 源码仍写 `* 32`，和真实 warp=64 不一致，不要信这个 builtin |
| LLVM TargetInfo `getWarpSize()` 返回 32、`getSharedMemorySize()` 返回 64 KiB | 这是 lowering 残留；运行时以 driver / `torch` 的 64 / 128 KiB 为准 |
| 同 warp 需要 `__syncwarp` | ivcore11 同 warp lane 是 lockstep，`__syncwarp` 是 no-op |

<a id="v150-compute-pipelines"></a>

### 4.6 计算管线：ALU / BFU / SFU / TCU

**已验证**；环境见本章硬件探针口径。

**是什么：**除矩阵乘加之外，V150 能执行普通浮点/整数运算、比较、位操作及专用数学函数。

本次对 1,048,576 个 FP32 元素分别执行下列操作，全部通过校验：

| 运算 | 实测核心指令 | 用途 |
| --- | --- | --- |
| `exp2(x)` | `ml_exp_f32` | softmax、指数衰减 |
| `sqrt(x)` | `ml_sqrt_f32` | 标准差、距离、归一化 |
| `rsqrt(x)` | `ml_rsq_f32` | RMSNorm、LayerNorm 的归一化因子 |
| 正确舍入的 `1/x` | `ml_rcp_f32` 加 FMA 修正 | 概率归一化、缩放 |

**怎么用：**

- softmax 可用 `exp(x)=exp2(x×log2(e))` 组织计算，缩放可与前面的乘法合并；需要重新验证数值误差。
- RMSNorm、LayerNorm 可使用 `rsqrt` 直接形成归一化因子。
- 正确舍入的倒数在本次汇编中包含额外 FMA 修正，因此应根据精度要求选择运算形式。
- 在矩阵计算外融合 scale、bias、激活或量化，可减少中间结果写回和再次读取。
- 整数索引、位操作、mask、数据转换都消耗执行资源。复杂 KV 寻址或量化路径即使减少显存流量，也可能增加这些指令的成本。

**特殊函数的计数口径已实测确认：**相同规模的恒等拷贝 SFU 计数为 0；加入上述任一数学函数后，SFU 为 16,384。`exp2` 与恒等拷贝的 BFU 计数相同，因此这里的 `exp2` 应按 SFU 路径分析，不能用 BFU 指令数量代替指数运算数量。

**计数器受控对照（已验证）**：`N=1,048,576`，grid=1024、block=256，FP32 输入范围 `[0.5,2.0]`，每元素执行一次操作；`tl.div_rn(1.0,x)` 用于倒数路径。各输出均通过 `atol=1e-6, rtol=1e-5` 对拍。

| kernel 操作 | BFU Instructions | SFU Instructions | 最大绝对误差 |
| --- | ---: | ---: | ---: |
| 恒等拷贝 | 204800 | 0 | 0 |
| `exp2` | 204800 | 16384 | 0 |
| `sqrt` | 200704 | 16384 | 0 |
| `rsqrt` | 204800 | 16384 | 1.1921e-7 |
| `div_rn(1,x)` | 290816 | 16384 | 0 |

BFU 是 ixKN 单列的指令统计类别；纯拷贝也有大量 BFU 计数，本文不补造其全部 opcode/物理管线对应关系。Matrix 计数对应 TCU 矩阵路径。ALU 包括普通浮点/整数、比较与地址运算，Single-Lane/多线程向量侧分别结合 SRF/VRF 观察。

**旧推断已更正**：过去根据完整 attention/GDN 中 BFU 多于 SFU，推断“`exp2` 主要进 BFU、不进 SFU”，证据不足，现由上述受控探针取代。历史 GDN2 `chunk_gdn2`（fp16，`4×2048×16×128×128`）BFU=16179200、SFU=2097152、Matrix=1638400 只保留为汇总计数，不能由此把单个函数归入 BFU。

判读时先核对具体指令与增量计数，再结合利用率、stall、访存和端到端时间判断瓶颈；SFU/BFU 指令数量的比例本身不足以定位瓶颈。SFU Instructions 为 0 只表示该次 kernel 没有计入 SFU 的指令，不说明硬件缺少该能力。字段解释见 [ixKN 指令构成](#95-ixkn-指令构成alu--sfu--bfu--tcu)。（2026-10-15）

<a id="v150-packed-arithmetic"></a>

#### 普通半精度打包运算及触发

**已验证**：保持 FP16 数据参与普通逐元素表达式时，当前编译器可以把两个元素放入一个 32-bit 寄存器，生成打包运算。BF16 必须按具体操作分别核对：

| 运算 | Triton 写法 | FP16 实测核心指令 | BF16 所测执行路径 |
| --- | --- | --- | --- |
| 加法 | `a+b` | `ml_pk_add_f16` | FP32 add + BF16 转换/重排 |
| 乘法 | `a*b` | `ml_pk_mul_f16` | `ml_pk_mul_bf16` |
| 最小值 | `tl.minimum(a,b)` | `ml_pk_min_f16` | FP32 min + BF16 转换/重排 |
| 最大值 | `tl.maximum(a,b)` | `ml_pk_max_f16` | FP32 max + BF16 转换/重排 |

触发依赖值类型、每线程元素分配和编译器模式；无需仅为了写出 FP16 加法而手工构造 half2，但任意布局不保证自动打包。若先转为 FP32，源代码已经改变计算精度，不能期待相同指令。

测试为每种 dtype 各 65536 个元素、BLOCK=1024、4 warps；输入为有限数，输出与对应目标精度参考逐元素一致。FP16 四种操作和 BF16 乘法为 8 VRF/thread；BF16 加法 10、min/max 11。没有覆盖 NaN、Inf 或次正规数的完整语义，也没有测定峰值吞吐。适用于激活、裁剪、缩放等逐元素融合；选择精度时把转换成本与模型误差一起考虑。（2026-10-15）

#### 半精度打包 FMA：FP16 / BF16

**已验证有对应硬件指令**：V150 的逐元素算术路径提供 `ml_fma_v2f16` 和 `ml_fma_v2bf16`。每个操作数将两个 16-bit 元素装入一个 32-bit 寄存器，一条指令分别执行 `d0=a0*b0+c0`、`d1=a1*b1+c1`；不是将两个乘积相加，也不是 `tl.dot` 的矩阵乘加。按运算数记作两次 FMA、4 FLOPs/线程指令，但这不是每周期吞吐或整卡峰值。（2026-10-15）

环境同本章硬件探针；对 65536 个元素执行 `d=a*b+c`，tile=1024、4 warps，FP16/BF16/FP32 分别测试显式 `tl.fma`、普通表达式及浮点融合选项。以下为实际汇编：

| 输入与写法 | 生成的核心算术指令 | 结论 |
| --- | --- | --- |
| FP16 `tl.fma(a,b,c)` | `ml_fma_v2f16` | 已生成打包半精度 FMA |
| FP16 `a*b+c`，`enable_fp_fusion=True` | `ml_fma_v2f16` | 所测普通表达式可融合 |
| FP16 `a*b+c`，`enable_fp_fusion=False` | `ml_pk_mul_f16` + `ml_pk_add_f16` | 所测路径变成独立打包乘法与加法 |
| BF16 `tl.fma(a,b,c)` | `ml_fma_v2bf16` | 已生成打包 BF16 FMA |
| BF16 `a*b+c`，融合选项开/关 | `ml_pk_mul_bf16` + FP32 add/转换 | 所测路径未融合，不能只靠普通表达式或融合开关保证使用 BF16 FMA |
| FP32 `tl.fma(a,b,c)` | `ml_fma_f32` | 普通 FP32 FMA 指令路径 |

显式 FP16/BF16 FMA 的向量寄存器均为 10/thread；这里确认指令能力与生成路径，没有测定其峰值算力或相对其他实现的端到端加速比。

**调用方式**：Triton 使用 `tl.fma(a,b,c)`，三个 operand 保持所需 FP16/BF16 类型，再检查实际汇编是否打包。CoreX 4.4.0 的 `iluvatar_fp16.hpp` 还提供 `__hfma(__half,...)` 和 `__hfma2(__half2,...)`：前者源码用 `__fp16` 表达式，后者用 `v2f16` 表达式。这里只核对了 C++ 头文件实现，C++ 调用的最终指令仍取决于实际编译参数；本节硬件指令证据来自已执行的 Triton 核。

**用途**：将 scale/bias、反量化、逐元素仿射变换或多项式激活组织为乘加，减少独立乘、加及部分临时结果。只有误差允许时才在半精度中间结果上使用；需要 FP32 累加的归约或矩阵任务仍按其精度要求选择路径，不能据“两个元素打包”直接认定算子会快两倍。

**数值边界（已验证）**：参考是在 CPU 上先用 FP64 计算量化后输入的乘加，再转换回目标 dtype。BF16 显式 FMA 的 65536 个结果全部与该参考相等；FP16 显式 FMA 有 1 个元素不逐位相等，最大绝对差为 `0.0009765625`，通过 `atol=rtol=0.001` 对拍。普通分离乘加存在中间舍入，不能要求它与融合结果逐位一致。

FP16 差异样例：`a=-0.389404296875`、`b=0.184326171875`、`c=-1.8525390625`；实卡输出 `-1.9248046875`，FP64 后转 FP16 的参考为 `-1.923828125`。该样例也不同于本次 FP32 中间结果后转 FP16 的参考；尚未定位舍入差异的根因，不能宣称所测 FP16 FMA 对所有输入均等同于严格参考的一次舍入。若算子要求逐位一致，应将此样例加入正确性校验。（2026-10-15）

#### 打包整数点积、位操作与触发

**已验证 4 路 INT8 点积累加入口**：CoreX C++ 的有符号 `__dp4a` 将两个 32-bit 输入各看成四个 INT8，执行 `acc + Σ(a[j]*b[j])`，结果为 INT32。输入在寄存器内打包，不要求调用者组织成完整二维矩阵。

```cpp
int result = __dp4a(packed_a, packed_b, accumulator);
// 三个参数均为 int；packed_a / packed_b 的四个字节是有符号 INT8。
```

使用 CoreX `clang++ -x ivcore --cuda-path=/usr/local/corex --cuda-gpu-arch=ivcore11 -O3` 编译后，4096 个线程结果与 CPU 四个 signed-byte 乘积加 acc 的参考完全一致，测试含负字节；编译所得 LLVM IR 调用 `llvm.bi.idot4(i32,i32,i32)`。这是逐线程打包整数点积入口，与 `tl.dot` 的矩阵 TCU 路径分开记录；本次未测其峰值或量化算子端到端收益。

**明确编译失败**：`__dp2a_lo(int,int,int)` 在同一工具链报：

```text
<inline asm>:1:2: error: invalid instruction
        dp2a.lo.s32.s32 v0, v0, v3, v4;
clang++: error: llc command failed with exit code 1
```

SDK 有声明不等于这张卡的当前编译路径可用，不将 `dp2a` 记为已支持。

**位操作与寄存器内数据整理（已验证）**：Triton 的安装版入口如下：

```python
from triton.language.extra.corex import libdevice
v = libdevice.byte_perm(a, b, 0x5410)  # 两个 32-bit 值中选取字节
count = libdevice.popc(a)             # 统计置位 bit
reversed_bits = libdevice.brev(a)     # bit 顺序反转
high_product = libdevice.mulhi(a, b)  # 整数乘积的高位，类型决定有/无符号
```

| 功能 | 实测指令或实现 | CoreX C++ 复核入口 |
| --- | --- | --- |
| 字节重排 | `ml_byte_permute_b32`；反汇编显示 `PRMT` | `__byte_perm` |
| 置位计数 | `ml_bcnt1_b32` / `POPC.ONE` | `__popc` |
| bit 反转 | `ml_brev_b32` / `BREV` | `__brev` |
| 乘积高位 | Triton signed INT32 为 `ml_mul_i64_i32` | 无符号 `__umulhi` 也已正确运行 |
| 漏斗移位 | 所测结果由 shift/OR 指令组合实现，不写成单条原生 funnel 指令 | `__funnelshift_r(a,b,5)` |

Triton 四项各对 65536 个 INT32 元素与整数参考对拍，全部相等；byte selector 为 `0x5410`，mulhi 使用 signed INT32。C++ 复核各 4096 元素，byte perm、popcount、bitreverse、unsigned mulhi 和 funnelshift 均完全正确。它们可用于量化打包/解包、mask 计数、索引与位布局整理；字节重排在同一线程的值内进行，跨 lane 交换需用 shuffle。（2026-10-15）

### 4.7 Global Memory 访问行为实测

以下结果基于 BI-V150 OAM、CoreX 4.4.0、ixKN 4.4.0。所有测试均为 64-lane warp。结论只区分两类可写事实：“程序有效带宽（端到端计时）”与“ixKN 内部吞吐/请求指标”；不要把后者外推成未测量的微架构机制。

#### 显存、缓存用途与 copy 有效带宽复核

**已验证**。

**有什么：**目标卡有 **32 GiB HBM、16 MiB L2**，并有可在 ixKN 中观察命中率的 L1 Vector Cache。

**有什么用：**

- HBM 承载模型权重、KV cache 和中间激活；容量决定能放下多少参数、token 与 batch。
- L2 可复用重复访问的数据；相邻任务复用同一权重或 KV tile 时，可通过调度和分块减少后端读取。
- 对低算术强度的向量算子与小 batch decode，减少读写字节数、避免临时张量通常很有价值。
- KV cache 的连续维、page 大小与 head 布局会影响访问跨度、加载效率及地址计算量。

本次 FP32 copy 探针的有效带宽：

| 有效输入规模 | 读取方式 | 有效带宽 |
| --- | --- | ---: |
| 4 MiB | 连续读取 | 约 881 GB/s |
| 32 MiB | 连续读取 | 约 554 GB/s |
| 32 MiB | 每隔 4 个元素读取一个 | 约 194 GB/s |
| 256 MiB | 连续读取 | 约 578 GB/s |

带宽按“有效读取字节+输出写入字节”除以时间计算，使用同一输入重复执行；小工作集可复用缓存。它们是**实际 kernel 的有效带宽**，用于估算工作负载时间，不是 HBM 理论峰值。跨步实验同时扩大了输入地址范围。

**怎么用：**让相邻线程尽量读取连续数据；尽量复用已经加载的 tile；融合反量化、scale 和后续计算，减少中间张量落地。评估压缩存储时，同时计算解码和布局转换的成本。

配置：FP32、每 block 256 线程、每 program 处理 1024 个元素，输出与 `x[::stride]` 逐元素一致；规模栏为有效输入字节数，stride=4 时源地址覆盖范围为其 4 倍。时间/有效带宽中位数分别为 9.519 µs/881.23 GB/s、121.146 µs/553.95 GB/s、345.108 µs/194.46 GB/s、929.431 µs/577.63 GB/s。计时按本章硬件探针 Graph 口径。（2026-10-15）

#### Stride 扫描：访问跨度与工作集同时变化

Kernel 对每个线程执行一次 FP32 读取和一次 FP32 写入，核心关系为：

```cpp
y[i] = x[i * stride];
```

测试配置：8,388,608 个线程、256 threads/block、32,768 blocks；逻辑读写量固定为 64 MiB；stride 取 1、2、4、8、16；预热 5 次，正式计时取 30 次平均。由于 stride 不同会覆盖不同范围的输入，该实验同时包含访存合并、缓存命中和物理工作集变化，不能只解释为 coalescing。

| Stride | 稳态时间 | 逻辑有效带宽 |
|---:|---:|---:|
| 1 | ≈0.116 ms | ≈578 GB/s |
| 2 | ≈0.191 ms | ≈352 GB/s |
| 4 | ≈0.330 ms | ≈204 GB/s |
| 8 | ≈0.617 ms | ≈109 GB/s |
| 16 | ≈1.149 ms | ≈58 GB/s |

主要现象：

- Stride=16 比 Stride=1 慢约 9.9 倍，逻辑有效带宽约降至十分之一。
- Stride=1 曾出现约 0.27 ms 的首次偏慢结果，但后续稳定在约 0.116 ms；插入 Stride=16 测试后，Stride=1 仍能恢复。根因未确认，不能直接归因于缓存预热或时钟。
- Stride=1 与 16 的动态 Global Memory 指令数、ALU 指令数完全相同，但执行时间差约 10.4 倍，说明“访存指令条数相同”不代表访存代价相同。

ixKN 对照：

| 指标 | Stride=1 | Stride=16 |
|---|---:|---:|
| Duration | 111.576 μs | 1160.65 μs |
| Executed Instructions | 4,456,448 | 4,456,448 |
| Multi-Lane Global Memory Instructions | 262,144 | 262,144 |
| Multi-Lane ALU Instructions | 2,621,440 | 2,621,440 |
| LSU Utilization | 97.00% | 99.66% |
| L1 Vector Cache Load Hit Rate | 0% | 0% |
| L2 Cache Load Hit Rate | 75% | 0% |
| L2 Cache to Memory Access | 916,428 | 8,894,232 |
| Global Memory Load Throughput | 280.08 GB/s | 430.79 GB/s |
| Global Memory Store Throughput | 280.08 GB/s | 26.92 GB/s |
| TCU Efficiency | 0% | 0% |

可确认的解释：

1. Stride=16 的 `L2 Cache to Memory Access` 约为 Stride=1 的 9.71 倍，且 L2 load hit rate 从 75% 降至 0%，支持内存访问路径是主要影响因素。
2. ixKN 的 `Global Memory Load Throughput` 不是程序有效带宽。Stride=16 的该指标更高，但完成相同数量有效元素所需时间更长。
3. `Throughput × Duration` 得到的估算流量会随跨步显著放大；在厂商未公开公式前，不能把它当作物理 HBM Read Bytes。
4. LSU utilization 接近 100% 只说明 load/store 资源高度活跃，不等同于达到 HBM 峰值，也不能单独证明瓶颈一定在 DRAM。

#### 固定工作集置换：分离工作集大小影响

为避免 stride 扫描中物理工作集不同，使用相同 32 MiB 输入和输出集合进行两种读取：

```cpp
// Linear
index = i;

// Permute：每个 256 元素 tile 内做双射置换
tile = i / 256;
lane = i % 256;
index = tile * 256 + (lane % 16) * 16 + lane / 16;
```

两种模式都通过逐元素正确性校验。

| 模式 | 稳态时间 | 逻辑有效带宽 |
|---|---:|---:|
| Linear | ≈0.116 ms | ≈579 GB/s |
| Permute | ≈0.1214 ms | ≈553 GB/s |

Permute 约慢 4.8%。ixKN 对照：

| 指标 | Linear | Permute |
|---|---:|---:|
| Duration | 111.134 μs | 123.038 μs |
| Executed Instructions | 3,932,160 | 4,718,592 |
| Single-Lane ALU Instructions | 1,179,648 | 1,179,648 |
| Multi-Lane ALU Instructions | 1,966,080 | 2,752,512 |
| Multi-Lane Global Memory Instructions | 262,144 | 262,144 |
| L1 Vector Cache Load Hit Rate | 0% | 74.75% |
| L2 Cache Load Hit Rate | 75% | 0.98% |
| L2 Cache to Memory Access | 916,756 | 915,880 |
| Global Memory Load Throughput | 281.19 GB/s | 1015.95 GB/s |
| Global Memory Store Throughput | 281.19 GB/s | 253.99 GB/s |
| LSU Utilization | 97.10% | 97.12% |

可确认的解释：

- Lane→Address 映射会显著改变 ixKN 观察到的缓存层级分布：Linear 主要表现为 L2 命中，Permute 主要表现为 L1 命中。不同层级的命中率不能相加，也不能据此反推 cache line 大小。
- 两种模式的 `L2 Cache to Memory Access` 仅相差约 0.096%，说明在相同工作集下，本次地址顺序变化没有显著增加最终后端请求数量。
- Permute 多执行 786,432 条 Multi-Lane Integer ALU 指令，增幅 40%，而 Global Memory 指令数不变；额外开销主要来自地址计算。
- 约 4.8% 的差异不能唯一归因于访存合并，因为地址计算和缓存层级行为同时变化。

<a id="v150-cache-policy"></a>

#### 缓存访问策略的机器指令验证

**已验证**。

**是什么：**当前后端支持 `tl.load(..., cache_modifier=...)`，会把策略编码到数据加载指令中。本次 FP16/FP32 copy 的默认、`.ca`、`.cg`、`.cv` 均正确：默认与 `.ca` 的数据 load 使用 `ca|mie`，另两种分别使用 `cg|mie`、`cv|mie`。

**怎么用：**可将缓存策略作为优化变量，分别评估一次性大块读取和重复读取。保持工作集、复用次数与访问布局一致，再看缓存命中和时间。这里已确认策略进入机器指令；具体绕过哪级缓存、是否带来收益，要依据目标负载的计数与计时，不能只按参数名称判断。

测试为各 8,388,608 个 FP16/FP32 元素、连续读取、tile 1024、4 warps，默认和三种修饰符共 8 个配置均逐元素正确；这里只将指令编码确认为可用能力，不把单次 copy 的时间排序作为缓存策略普适收益。取舍需另做固定工作集与复用模式的受控实验。（2026-10-15）

#### 对 Kernel 优化的直接指导

1. 优先看程序有效字节数除以无 profiler 时间；不要只看 ixKN throughput 字段。
2. 对比布局时固定数据规模、dtype、线程数和工作集，再比较 L1/L2 hit、L2→Memory 请求、地址计算 ALU 和 Duration。
3. 动态访存指令数相同不代表内存事务量相同；应同时检查后端请求数和缓存命中。
4. 地址重排可能减少某层级 miss，却增加整数地址计算；必须用端到端时间判断净收益。
5. 当前证据不足以确定 BI-V150 的最小合并事务、L1/L2 cache line、缓存分配策略或 ixKN throughput 公式，**不把这些写成硬件定论**；本文到此为止，不再展开未测项。

### 4.8 全局原子操作：并行更新与结果合并

**已验证**。

**是什么：**多个线程竞争同一地址时，以原子方式完成更新。本次实测以下操作全部正确：

| 操作 | 实测执行方式 | 用途 |
| --- | --- | --- |
| INT32 原子加 | `ml_lsa_atomic_add_a64_i32` | 路由计数、直方图、索引分配 |
| FP32 原子加 | `ml_lsa_atomic_add_a64_f32` | scatter-add、分块累加 |
| FP16 原子加 | `ml_lsa_atomic_add_a64_f16` | 半精度结果并行汇总 |
| BF16 原子加 | `ml_lsa_atomic_add_a64_bf16` | BF16 结果并行汇总 |
| INT32 CAS | `ml_lsa_atomic_cmpswap_a64_b32` | 状态竞争、条件更新 |
| FP32 atomic max | 整数 min/max 原子指令组合 | 最大值汇总；本次含正负数校验 |

原子加探针使用 65,536 次更新汇总到 256 个地址，结果全部准确；它确认功能与指令路径，不用于推断不同精度的数值误差上限或高竞争吞吐。

**怎么用：**先在寄存器或 shared 内聚合，再减少向全局内存发出的原子更新数量。浮点结果需要考虑累加顺序；高竞争地址会串行化，不能仅因有原子指令就假定吞吐高。

原子加输入为常量 1，256 个输出各累加至 256；CAS 对 65,536 个独立 INT32 地址执行 `0→7`，全部正确；比较值和新值在 Triton 中显式构造成与指针形状匹配的 INT32 tensor。FP32 max 的偶数 bin 全为负候选、奇数 bin 为正候选，初值为负无穷，均与预期最大值完全一致。对应 max 汇编包含 `ml_lsa_atomic_min_a64_u32` 与 `ml_lsa_atomic_max_a64_i32`，不写成原生浮点 max 单指令。（2026-10-15）

#### 原子操作的内存顺序与附加指令

**已验证内存顺序会改变等待与缓存维护指令**。当前入口可写：

```python
# 仅在算法不依赖该原子操作发布/获取其他数据时考虑 relaxed：
tl.atomic_add(counter_ptr + offsets, values, sem="relaxed", scope="gpu")
```

| `sem` | 相同 INT32 atomic add 之外的所测序列 |
| --- | --- |
| `relaxed` | 没有该测试中 acquire/release 所增加的等待与 `wbinv` |
| `release` | 原子操作前增加 `sl_wait vmcnt(0) smcnt(0)` |
| `acquire` | 原子操作后增加等待和 `ml_lsa_wbinv` |
| `acq_rel` | 同时出现前后等待及 `ml_lsa_wbinv` |

四组均 `scope="gpu"`，65536 次 INT32 加 1 汇总到 256 个地址，每 CTA 256 线程；kernel 完成后由主机读取，四组计数均为 256，VRF=4/thread、shared=0。这里只验证该用法下的指令变化与结果，不覆盖完整内存一致性语义，也不将缺少 `wbinv` 直接写成性能收益。

`sem` 决定原子操作对其他内存访问的排序，不改变计数更新本身的原子性。锁、发布数据后置 flag、生产者/消费者等协议不能仅为减少指令改成 relaxed；按算法需要选语义，并先验证协议正确性。（2026-10-15）

## 3. Shared Memory 与矩阵路径实测

共享内存用于 GEMM/Attention tile 缓存与重复使用、转置及线程间布局重排、矩阵 operand staging、跨 warp 数据交换和局部归约合并。为下一轮数据预留 staging 空间时，双缓冲要预算两份数据。每 SM 的 128 KiB 按驻留 block 分配；例如 64 KiB/block 时 shared 容量最多容纳 2 个 block，128 KiB/block 时最多 1 个；实际还受其他资源限制。

布局优化可尝试 padding、转置和 XOR swizzle，但 store 与 consumer load 必须配套。32-bit 标量探针的模 64 规律不自动适用于 BF16 向量或 SME；后面保留两类路径及完整 attention 的反例。

### 3.1 显式 shared-store 标量探针

一个 block 固定 64 个线程，即一个 64-lane wave。探针读写 32-bit shared-memory word，并通过 host 回读验证结果。

#### 连续地址

配置：`grid=(8192,1,1)`、`block=(64,1,1)`、64 次迭代，所有 lane 访问自身的连续 32-bit word。

- 正确性：`validation=passed`。
- shared-store bank conflict：0；shared-load bank conflict：0。
- multi-lane shared-memory instructions：532480；SME memory instructions：0；matrix instructions：0。
- 动态 shared memory：256 B/block。

结论：64 个 lane 访问连续且互异的 32-bit shared 地址时，BI-V150 的读、写均无 bank conflict。

#### 全 lane stride 扫描

地址模式为 `word_index = lane * stride_words`。所有测试的 grid、block 和迭代次数与上一节相同，八项测试都通过正确性验证。

| stride（32-bit word） | store conflict/每次 wave 访问 | load conflict/每次 wave 访问 |
|---:|---:|---:|
| 1 | 0 | 0 |
| 2 | 4 | 4 |
| 4 | 12 | 12 |
| 8 | 28 | 28 |
| 16 | 60 | 60 |
| 32 | 62 | 62 |
| 64 | 63 | 63 |
| 128 | 63 | 63 |

归一化方法：store 总冲突数除以 `8192 * 64`；load 总冲突数除以 `8192`。结论：stride 增大时冲突递增；stride 64 和 128 达到本扫描观察到的最大值 63。

#### stride=64 的 XOR-lane 布局验证

固定 `stride_words=64`，写和读使用同一个地址映射。

| 地址映射 | 正确性 | store conflict/每次 wave | load conflict/每次 wave | 动态 shared |
|---|---|---:|---:|---:|
| `lane * 64` | 通过 | 63 | 63 | 16384 B/block |
| `(lane * 64) XOR lane` | 通过 | 0 | 0 | 16384 B/block |

ixKN 中线性布局 duration 为 1209.10 us，XOR-lane 为 135.423 us；这是 profiler 探针时长，不是生产 attention kernel 基准性能。

结论：对该 64-lane、32-bit stride-64 读写模式，在不增加动态 shared memory 的条件下，同步将读和写改为 XOR-lane 映射可消除读、写 bank conflict。

#### 两 lane 地址关系扫描

探针只让 lane 0 访问 word 0、lane 1 访问 word `delta_words`，其余 62 个 lane 不访问 shared memory。配置：`grid=(8192,1,1)`、`block=(64,1,1)`、64 次迭代；`delta_words=1..128` 的每项均通过正确性验证。

| word 地址差 | shared-store conflict | shared-load conflict |
|---|---:|---:|
| 1..63 | 0 | 0 |
| 64 | 524288 总计，即每次两-lane store 访问 1 | 8192 总计，即每次两-lane load 访问 1 |
| 65..127 | 0 | 0 |
| 128 | 524288 总计，即每次两-lane store 访问 1 | 8192 总计，即每次两-lane load 访问 1 |

结论：在该 32-bit scalar shared-memory 访问测试中，word 地址差为 64 的倍数会冲突；在已扫描的其余差值中不冲突。因此，用于布局规避的实测 bank 等价周期为 64 个 32-bit word：需要让同一 wave 内并发访问的 word index 对 64 取余后尽量不同。该实验不赋予硬件 bank 物理编号；ixKN 的冲突计数不提供 bank 标签。

#### MSA BF16 D128 的真实 Q staging 布局复现

生产 `_gqa_sparse_fwd_direct` 在 BF16 `(1,8192,16,96)` 路径的 LLIR 显示，源码
第 229、233 行的 `q_lo`、`q_hi` 加载被降为 shared store。地址由硬件线程号
`t = threadIdx.x` 计算：

```text
byte_offset = ((t & 7) << 3)
            | ((t & 8) ? 384 : 0)
            | ((t & 16) << 5)
            | ((t >> 4) & 2)
            | (t & 64)
```

每个线程向 `4096 + {offset, offset+4, offset^128, (offset^128)+4}` 和
`5120 +` 同一组偏移各写入 BF16 值。该地址公式已由 LLIR 的 `%139/%141/%143/%145`
及 `%150/%151/%152/%153` 直接确认。

精确 C++ 探针结果：`msa_q_shared_store_probe`，grid `(8192,1,1)`、block
`(128,1,1)`、64 次迭代、6144 B 动态 shared memory。它按上述地址公式执行相同的
Q-low/Q-high 四次 BF16 写入，写后 barrier 并按同地址读回；`validation=passed`。

- shared-store bank conflict：50,331,648，总数除以 `8192 * 64` 后为每 block
  每轮 96。
- shared-load bank conflict：786,432，总数除以 `8192` 后为每 block 每轮 96。
- multi-lane shared-memory instructions：8,519,680。
- shared-memory utilization：99.52%。
- dynamic shared memory：6144 B/block；local memory：0 B/thread。

结论：真实 MSA BF16 D128 的 Q staging store 本身存在可复现的 shared store/load
bank conflict。该实验只覆盖 Q staging，不能据此把生产 kernel 的全部总冲突归因于
Q；输出重排及其他后端生成的 shared 操作仍须分别验证。

#### MSA Q staging 地址布局筛选

在上一节的精确 Q staging C++ 探针中，保持 128 线程、6144 B shared、全部地址
互异、读回校验和其余指令结构不变，只改变 `byte_offset` 的 shared 地址映射。
四个候选均通过 `validation=passed`。

| 布局 | 每 block 每轮 store conflict | 每 block 每轮 load conflict | ixKN duration |
|---|---:|---:|---:|
| baseline | 96 | 96 | 876423 ns |
| b4：`offset ^= (lane & 16) << 2` | 64 | 64 | 714730 ns |
| b5：`offset ^= (lane & 32) << 2` | 96 | 96 | 874173 ns |
| b4-b5 | 64 | 64 | 716596 ns |

结论：`b4` 将 Q staging 的读、写冲突均降低 33.3%，`b5` 没有可测收益，二者组合
也不优于 `b4`。该 ixKN duration 仅用于该控制探针的方向判断，不代表 production
attention 的性能。下一步只应尝试将 `b4` 映射转移到真实 Q staging，不能再扩展
`b5` 方向。

#### 显式 Q shared buffer 能进入 QK 左操作数

显式 Q shared-memory 探针在真实 D128-split QK 形状 `[8,64] × [64,32]`
上使用 `tle.gpu.alloc` 创建 Q buffer。`max_phase=1` 已实际编译、运行并通过
`torch.testing.assert_close`。

TTGIR 实测：

- Q buffer 为 `ttg.local_alloc`，类型为
  `memdesc<8x64xbf16, #shared1, #smem, mutable>`；
- Q buffer 的 `ttg.local_load` 直接生成 QK 左操作数，编码为
  `dot_op(opIdx=0, kWidth=2, useSme=0)`；
- K buffer 为独立 `ttg.local_alloc`，其右操作数编码保持 `useSme=2`；
- `tt.dot` 的两个输入分别是上述 Q local-load 与 K local-load。

结论：显式 Q shared buffer 可以真实进入 BI-V150 的 QK dot operand，不会退回为
普通 global Q load。下一步需要比较不同 Q shared layout 在 LLIR 中生成的 store
地址，再选择是否把对应布局并入 production kernel。

### 3.2 Triton BF16 tensor-core shared-memory 探针

配置为 2 warps、1 stage、`grid=(8192,1,1)`、`block=(128,1,1)`。下表数值为每个 program，所有 shape 均通过 `torch.testing.assert_close`。

| case / 矩阵形状 | store conflict | load conflict | matrix 指令 | SME 指令 | shared 指令 | 动态 shared | 向量寄存器/线程 |
|---|---:|---:|---:|---:|---:|---:|---:|
| qk: `(8,64) x (64,128)` | 48 | 0 | 32 | 16 | 80 | 17408 B | 30 |
| pv: `(8,128) x (128,64)` | 96 | 0 | 32 | 16 | 96 | 18432 B | 21 |
| k64_n64: `(8,64) x (64,64)` | 48 | 0 | 16 | 8 | 48 | 9216 B | 21 |
| k128_n128: `(8,128) x (128,128)` | 96 | 0 | 64 | 32 | 160 | 34816 B | 38 |
| m16_n64_k64: `(16,64) x (64,64)` | 0 | 0 | 16 | 10 | 48 | 10240 B | 25 |

所有 case 的 local memory 均为 0 B/thread。

#### 已验证的矩阵探针规律

- 在已测的 M=8 四个 BF16 矩阵 shape 中，都存在 shared-store conflict，且 shared-load conflict 为 0。
- 固定 K=64 时，N 从 64 变为 128，store conflict 保持 48/program；固定 K=128 时，N 从 64 变为 128，保持 96/program。
- 在该 2×2 对照中，K 从 64 变为 128 时，store conflict 从 48/program 增为 96/program；N 变化不改变该数值。
- `M=8,N=64,K=64` 的 A operand 有 4 条显式软件 shared store、4 条 SME call；K=128 时二者都为 8 条。该证据不能把冲突唯一归因给其中任意一类指令。
- `M=16,N=64,K=64` 的 A operand 不再有显式软件 shared store，变为 1 条 SME call；B operand 为 4 条 SME call。该 case 的读写冲突均为 0。
- TTGIR 对照：M=8 的 A operand 是 `useSme=0`，M=16 是 `useSme=1`；B operand 在两者中均为 `useSme=2`。
- 已检查的 SME load lowering 只消费 `useSme` 标志，未发现 M=8/M=16 的显式 shape 分支；当前可读的后端实现中也未找到设置该标志的规则。

### 3.3 使用边界

- “word index 对 64 取余避免重合”是 **32-bit scalar shared 读写探针** 的实测结论，不能直接替代对 BF16 向量化 store、SME load 或 production kernel 的独立验证。
- BF16 tensor-core 探针已证实 store conflict 与编译生成的显式 shared store / SME 路径有关。本知识库**不**把每个 conflict 唯一归因到某一条机器指令；取舍以完整核的 store/load 计数 + 无 profiler 正式计时为准。
- ixKN duration 只用于解释探针硬件行为；生产 sparse-attention 的取舍必须在正确性通过后，以普通计时和正式 workload 的结果决定。

### 3.4 线程同步与访存完成等待

**已验证**；2026-10-15 矩阵和 shared 往返汇编。

**有什么：**普通线程块同步使用 `sl_barrier`；访存路径可见 `sl_wait`，SME 的 IR 有专门 wait-count。

**有什么用：**block 内 shared 数据交换需要正确安排线程同步；消费者读取搬运结果之前，需要满足该搬运路径的完成条件。多个 warp 协作及 shared buffer 循环复用时，尤其要明确生产、消费和复用的先后顺序。

### 3.5 各级数据搬运的入口与限制

| 数据从哪里到哪里 | 触发入口与作用 | 证据和边界 |
| --- | --- | --- |
| Global→寄存器 | `tl.load`，或 C++ 普通 pointer/vector 读取 | `ml_lsa_load_*`；实际粒度受对齐、mask、布局影响 |
| 寄存器→Global | `tl.store` | `ml_lsa_store_*`；与上游计算融合可减少中间写回 |
| Global→Shared 矩阵 staging | 符合条件的 dot operand load，必要时显式 `stride=` | `sl_sme_load_*` + `g2scnt` 等待；普通二维 copy 不保证 SME |
| 寄存器↔Shared | `tle.gpu.alloc(...,scope=tle.gpu.smem,nv_mma_shared_layout=False)`，再 `local_ptr` 读写或 `copy` | 普通路径为 `ml_slb_*`，实际插入 barrier；不是自动获得矩阵布局或硬件异步 |
| 同 warp 不同 lane 的寄存器 | `__shfl*`，本次 `__shfl_xor(x,32,64)` | 完整 Warp64 正确，反汇编显示 `SPERMUTE.B32` |
| 主机↔Global | pinned buffer 和非阻塞 copy | 功能和单向带宽已测，计算重叠要另验 |

**宽类型不保证等宽机器指令**：本次 C++ `uint4` 读取并 XOR 四字段，4096 个输出均正确；其 LLVM IR 为一次 `<2 x i32>` load 加两次 i32 load，没有保留成一条 128-bit load。只能说 vector 接口可用，不能据 `uint4` 名字宣称发出一条 128-bit 指令。

**跨 lane 与线程内整理分开选**：量化字节 packing 先看 `byte_perm`，lane 之间交换看 shuffle，跨 warp/矩阵 staging 再看 shared/SME。额外层级意味着可能增加搬运、同步和片上资源占用。（2026-10-15）

## 3. Triton/TLE 编程与编译

### 5. 编程栈

```text
Python  / PyTorch 2.7.1+corex
        │  torch.cuda、CUDA stream/event、大部分 Aten 算子
        ▼
Triton 3.6  (backend=corex)
        │  @triton.jit → TTIR → TTGIR → LLIR → cubin
        │  可选 TLE（triton.experimental.tle.language）
        ▼
CoreX runtime  (libcuda.so.1 + ixcc/LLVM)
        ▼
ivcore11 硬件
```

写算子的四条路：

1. **CoreX PyTorch**：`einsum` / `matmul` / `softmax` 等。正确、慢，适合对照。用于正确性对照。
2. **Portable Triton**：`tl.load` / `tl.store` / `tl.dot` / `tl.make_block_ptr`。MSA prefill、SageAttention 动态 KV、GDN2 优化核主体都走这条。
3. **TLE**：可用子集是 `alloc(smem, nv_mma_shared_layout=False)` / `local_ptr` / `copy` / 小 tile 的 tile 原语 / capacity=1 的 `pipe`；矩阵仍用 `tl.dot`。`wgmma`、barrier、`set_layout`、`warp_specialize` 本机不可用。详见 [第 7 节](#7-tle)。
4. **IxFormer CUDA 库**：厂商注意力 / 量化 / MoE。Flash、Paged、MLA 有；**没有** MiniMax 式 per-head top-k 稀疏核。见 [第 13 节](#13-厂商库-ixformer)。

CUDA C++ / `nvcc` 在 `/usr/local/corex-4.4.0/bin` 里有；本文算子路径以 Triton/IxFormer 为主，不用手写 device code 作为默认方案。厂商已编好的注意力在 IxFormer 里。

### 6. Triton DSL

#### 6.1 Launch 参数

`CorexOptions` 默认：

```text
num_warps=4, num_ctas=1, num_stages=3, warp_size=64, maxnreg=None
enable_fp_fusion=True, enable_reflect_ftz=True
launch_cooperative_grid=False, launch_pdl=False
use_sme=0   # 运行时按 tensor 连续性自动置位
```

实际经验：

| 参数 | 建议 |
| --- | --- |
| `num_warps` | 4 最稳。SageAttention D=64 只用 4，D=128 才试 8。warp=64，8 warp 就是 512 线程 |
| `num_stages` | **先当 1**。MSA bf16 prefill：3 要 132100 B，2 同样超 128 KiB，只有 1 能过。不要假设 stage 和 smem 线性 |
| `maxnreg` | 不传。H100 的 168/128 对天数没有对应关系 |
| `num_ctas` | 保持 1 |
| `launch_pdl` | 不要设。capability (7,1) 开不了 |

##### Stage 深度、shared 预算与驻留

**已验证**。

**是什么：**stage 控制编译器流水线及缓冲安排，会消耗 shared memory。它是利用搬运和计算路径的编译参数。

本次相同 BF16 `256³`、tile `32³` 测得：

| `num_stages` | shared/block | 寄存器/线程 | 正确性 |
| --- | ---: | ---: | --- |
| 1 | 4 KiB | 16 | 通过 |
| 2 | 8 KiB | 16 | 通过 |
| 3 | 12 KiB | 16 | 通过 |
| 4 | 16 KiB | 16 | 通过 |

**怎么用：**用 stage 隐藏数据准备开销时，同时计算驻留减少的代价。先测试较浅流水，再在 shared 容量允许的范围增加；这组小 GEMM 的耗时没有随 stage 增加而持续下降。上表的线性容量关系只对这组 kernel 成立。

配置均为 BF16 输入、FP32 累加/输出、4 warps，全部与同一 FP32 参考对拍通过；时间按本次 Graph 口径，中位数随 stage 1/2/3/4 分别为 7.094/6.550/6.662/6.898 µs。该小核可用于说明容量代价与非单调收益，不据此宣称 stage=2 对其他算子最优。stage=1/2/3/4 的所测汇编均可见 `g2scnt(0)` 等待，不能根据 stage 数或更多 SME load 的静态位置数直接宣称多请求重叠成立。（2026-10-15）

#### 6.2 循环：这是天数卡最大的编译/语义坑

| 写法 | 天数上会发生什么 |
| --- | --- |
| `tl.static_range(0, KV_BLOCKS)` 且 `KV_BLOCKS` 随序列变 | **编译期完全展开**。T=8192、BLOCK_N=32 就是 256 次拷贝。SageAttention 第一阶段编了约 10 小时，最后二进制太大在 autotune launch OOM |
| `for start_n in range(0, kv_len, BLOCK_N)` | 关 `STATIC_KV` 后 **不会把 KV tile 转完**（基本只跑第一块）。对拍误差纹丝不动就是这个原因 |
| `while start_n < kv_len:` + 每次从基地址 `ptr + start_n * stride` | **能转完、能对拍**。SageAttention 第二阶段正确性 7 passed，bench 出到 16384 |
| `tl.range(..., disable_licm=True, num_stages=1)` | MSA decode / 部分 TLE 循环在用。动态长度用这个，不要 `static_range` |

天数 `range` 不可靠时，寻址也不要 `ptr += BLOCK` 累加，改成每次从基地址加偏移。静态路径能过，是因为展开后每块都是独立 load。

#### 6.3 特化与对齐

天数会对指针对齐做 specialization，变长 metadata 切片后对齐一变就重新编译。MSA 的做法：

```python
@triton.jit(do_not_specialize_on_alignment=["seq_lens", "prefix_lens"])
```

标量 load 用的指针不需要对齐特化。动态长度参数还可以：

```python
@triton.jit(do_not_specialize=["decode_query_len"])
```

##### 对齐影响打包加载与寄存器

**已验证**。

**是什么：**地址对齐会影响每条加载指令读取的数据宽度。连续 tensor 切出一个 view 后，即使 shape 不变，首地址也可能失去原来的对齐。

本次 FP16 copy 对同样 8,388,608 个元素测试：

| 输入首地址 | 实际数据加载 | 静态数据 load 数 | 向量寄存器/线程 |
| --- | --- | ---: | ---: |
| 原始对齐地址 | `ml_lsa_load_dword`，32-bit 打包读取 | 2 | 6 |
| 偏移 1 个 FP16 元素，即 2B | `ml_lsa_load_ushort`，16-bit 读取 | 4 | 8 |

两者均正确。数量是所测汇编中的静态指令位置数，不是整次 kernel 的动态访存条数。

**怎么用：**设计 KV page、量化 block、head stride 和 packed 数据时，保留适合数据类型的对齐。不要为了省少量 padding，把每一行都变成不利于打包加载的起始地址。`multiple_of` 等提示只能声明真实成立的对齐。

测试 tile=1024、4 warps，无边界 mask；原始输入首地址模 16 为 0，偏移后为 2。FP32 也测试原始地址与偏移 1 个元素，结果均正确，所测 load 仍为 dword，未观察到同样的指令宽度变化。对齐影响与 dtype 和生成布局有关。（2026-10-15）

#### 6.4 Autotune

- `triton.autotune` / `triton.heuristics` 都能用。
- 候选不要含随问题规模变的 constexpr（例如 `KV_BLOCKS = ceil(T / BLOCK_N)`），否则每个 seq 编一份巨型核。
- `TRITON_PRINT_AUTOTUNING=1` 会打印每次搜索。
- `triton.knobs.autotuning.adjust_block_size = False`：MSA benchmark 关掉自动改 BLOCK，避免后端改变预期的 BLOCK 语义。
- 大 grid + 高 spill 的候选会在 `kernel.run` 时 `Triton Error [CUDA]: out of memory`。进程内 `allocated` 可能只有几百 MB，是 **local memory × block 数** 撑爆 32 GB，不是激活张量。
- SageAttention D=128 每个 seq 试 3 组 tile（64×64 / 128×64 / 128×32），key 含 `qo_len`/`kv_len`，换长度就重新搜。32768 仍 autotune OOM。

#### 6.5 Load / MMA

能用：

- `tl.load` / `tl.store` / `tl.make_block_ptr`
- `tl.load(..., stride=row_stride)`：为矩阵 operand 显式提供行跨度；只有满足消费者和布局条件才触发所测 SME，见 [SME 触发矩阵](#v150-sme-triggers)
- `tl.dot`（f16/bf16/f32/i8；FP8 仅小核）
- `tl.fma`（已实测 FP16/BF16 可分别生成 `ml_fma_v2f16` / `ml_fma_v2bf16`；普通表达式不保证同样融合，数值边界见“半精度打包 FMA”）
- `triton.language.extra.corex.libdevice.byte_perm/popc/brev/mulhi`（整数路径已运行核验，见 [整数与重排](#v150-integer-paths)）；转换和复合函数见 [实际执行路径](#v150-conversion-math)
- `tle.load(..., is_async=True)`（小核数值 PASS；TTIR 只打 `tt.load.async`，汇编退化为同步 LSA/SLB，不是 TMA/SME。详见 [7. TLE](#7-tle)）
- `tl.inline_asm_elementwise`（GDN2 softplus；约束必须 `=r` 不是 `=f`，写错会 abort 进程）

不能用 / 不要用：

- NVIDIA `TensorDescriptor` + TMA（capability&lt;90 的 pass 会改写成 pointer）
- `tle.gpu.alloc(..., nv_mma_shared_layout=True)` → `iluvatar TLE alloc does not support nv_mma_shared_layout=True`
- `tle.gpu.wgmma` / `set_layout` / barrier / `warp_specialize`（见第 7 节；不要当默认路径）
- `q.to(tl.float8e4nv)` 再和 FP8 K 做 MMA（bench 规模 spill）
- kernel 里读取非 constexpr 全局变量


INT8 与 FP8 的额外兼容性规则：

- `INT8×INT8→INT32` 必须在 `tl.dot` 显式传 `out_dtype=tl.int32`，并使用 INT32 accumulator。
- INT8 tile 不能只凭编译成功或小 shape 推断正确；已出现 `32×64×32` 错误而 `32×32×32` 正确的情况，autotune 每个候选都必须先对拍。
- FP8 masked load 的 `other=0` 可能因整数常量无法隐式转成 FP8 而编译失败；只有所有地址确定合法时才能取消 mask。
- JIT kernel 内使用的 tile 常量应作为 `tl.constexpr` 参数传入，不能依赖普通 Python 全局变量。

#### 6.6 SME（Shared Memory Engine / 矩阵 load）

<a id="v150-sme-triggers"></a>

SME 是面向二维矩阵 tile 的搬运与布局准备路径，TCU 执行矩阵乘加。要触发当前 Triton 的 SME，需同时考虑前端候选选择、load 的布局和后续 dot operand；**二维 load 或单独传 `stride=` 都不保证触发**。

**自动选择规则（已检查安装版源码，并用下表核验）**：

- CoreX 环境 `torch.corex == True`，且未设置 `TRITON_DISABLE_SME=1`。
- 支持候选 dtype 为 FP16、BF16、FP32、INT8；host tensor 原始 rank 至少为 2，去掉 size=1 维度后仍至少二维。
- 前端行主序候选：tensor contiguous，最后一维可被 `64/element_size` 整除。列主序候选：tensor 非 contiguous，倒数第二维满足该粒度。FP16/BF16 为 32 元素，FP32 为 16，INT8 为 64。
- 后端还要求可识别的矩阵 operand、允许 SME 的布局和有效行跨度。安装版 `SmeLoad.cpp` 检查 dot operand 的 `useSme`，优先取显式 input stride，否则尝试从地址表达式恢复。

这是候选与 lowering 规则，不是任意 stride、非 contiguous 或所有 mask 都成立的硬件承诺；64B 也不据此解释为 cache line 或所有访存的最小事务。

安装版编译器对 ivcore11 使用 SME version 1，并运行 `add_matmul_smeload` pass；源码中的 FP16/BF16 布局名为 `rowxfb16/colxfb16`，FP32 为 `rowxfb32/colxfb32`，INT8 为 `rowxfb8`。这些是实现线索，具体布局是否执行仍以生成产物为准。已测普通 TLE `gpu.copy` 不走 SME。该路径主要用于 GEMM、Attention 的矩阵 operand staging。

**已验证的触发矩阵**：每项在独立进程中运行；FP16 输入 A/B 均为 `32×32`，地址仍按相同二维 tile 构造，4 warps、1 stage，FP32 输出。dot 与 FP32 参考按 `atol=rtol=0.025` 校验，正常 dot 最大误差 7.6294e-6；逐元素加法按半精度加法后转 FP32 对拍。

| 变化 | 生成 SME | 正确性与含义 |
| --- | --- | --- |
| host 输入保持二维，自动选择 | 是 | 通过；已生成 `sl_sme_load_16x1b64_rowxfb16` |
| 同一数据 flatten 为一维传入，自动选择 | 否 | 通过；变为普通 global load，矩阵仍用 TCU |
| 一维输入，在 dot operand load 显式传正确 `stride=32` | 是 | 通过；恢复 SME |
| 二维输入，在 dot operand load 显式传 `stride=32` | 是 | 通过 |
| 二维 load 只用于逐元素 `a+b` | 否 | 通过；没有 dot 消费者 |
| 上一行的 load 再加 `stride=32` | 否 | 通过；stride 不是通用二维搬运加速开关 |
| dot 的 K 维只保留前 29 项，其他项 masked load 为 0 | 是 | 自动/显式 stride 两种均通过，最大误差 3.8147e-6；另有普通 load/修补指令，不推广为任意 mask 无成本 |
| 二维输入，在启动参数传 `use_sme=0` | 是 | 本路径 metadata 仍为自动重算的 `use_sme=7`，不能据启动实参判断是否关闭 |
| 一维输入，在启动参数传 `use_sme=3` | 否 | 本路径 metadata 被重算为 `use_sme=4`，不能据启动实参判断是否打开 |
| 新进程设置 `TRITON_DISABLE_SME=1`，二维自动路径 | 否 | 通过，metadata 的 `use_sme=0`；可用于受控对照 |

`use_sme` 是按函数实参索引的候选位图，不是是否发出 SME 的最终证据；上述 7/4 还包含输出 tensor 对应的候选位。行跨度 `stride` 以元素为单位，必须与实际地址表达式一致，不能为错误对齐或越界访问兜底。

**已验证写法**：下面是单 CTA `32³` FP16 矩阵乘的完整 kernel。示例不带边界 mask，调用方必须保证 A/B/C 所有地址合法；`lda/ldb` 是实际行跨度，输出 C 为行连续 `32×32` FP32。

```python
import triton
import triton.language as tl

@triton.jit
def dot_tile(A, B, C, lda: tl.constexpr, ldb: tl.constexpr):
    m = tl.arange(0, 32)
    n = tl.arange(0, 32)
    k = tl.arange(0, 32)
    a = tl.load(A + m[:, None] * lda + k[None, :], stride=lda)
    b = tl.load(B + k[:, None] * ldb + n[None, :], stride=ldb)
    acc = tl.dot(a, b, input_precision="ieee")
    tl.store(C + m[:, None] * 32 + n[None, :], acc)

# 连续 32×32 FP16 A/B、32×32 FP32 C：
# dot_tile[(1,)](a, b, c, 32, 32, num_warps=4, num_stages=1)
```

检查汇编是否同时有 `sl_sme_load_16x1b64_rowxfb16`、`ml_matrix_mad_f32_f16_m16n16k16` 和 `sl_wait ... g2scnt(0)`；IR 中相应有 SME load 与 `llvm.bi.sl.waitcnt`。线程到达 barrier 不等于 SME 已完成，buffer 消费与复用必须满足搬运等待条件。

**资源例子（已验证）**：另一组 FP16/BF16 `512³` GEMM、tile `32³`、4 warps、1 stage 中，显式指定两个输入行跨度后，普通 global load/shared store 减少，VRF 从 20 降到 16/thread，shared 均为 4096 B/block。只确认该 kernel 的资源变化，不宣称普适性能收益。

**明确数值失败**：同一 `32³` FP16 load/dot 探针中，把 A/B load 结果都 `.to(tl.float32)` 后再 dot，最大绝对误差约 **31.99448**；SME 消失，所测汇编仍出现 FP16 matrix mad。根因未定位，不能当作正确路径，也不能据此推断所有 FP32 dot 或所有类型转换错误。调整 operand 类型、转换位置和布局后必须重新对拍。（2026-10-15）

#### 6.7 Benchmark harness 和 N 卡的差别

天数这份 `triton.testing`：

1. **`do_bench(warmup=, rep=)` 的单位是毫秒，不是迭代次数。**  
   `warmup=25, rep=100` 表示大约预热 25 ms、重复测量 100 ms。kernel 若单次 452 ms，实际可能只跑很少几次。若使用 `warmup=200, rep=300` 在天数上 prefill 一档 1.5–10 s 时，每个 shape 大约只跑十几次。
2. **`Benchmark` 要求 `len(x_vals) == len(x_names)`。**  
   `x_names=["shape"]` 配 `(B,S,H,D)` 四元组会炸。天数卡把横轴拆成四个名字，再用包装函数拼回 `shape`。
3. **画图横轴必须是数值。** 不能把元组当 `x`。
4. 理论峰值辅助函数 `get_max_tensorcore_tflops` 按 SM 数 × 4 估算，**不是官方白皮书峰值**。实测 attention 核大约 2.5–3 TFLOPS（同公式 H100 是几百 T），不要拿辅助函数当交付指标。

计时本身仍用 `torch.cuda.Event`，和 N 卡一样。

### 7. TLE

TLE 在 BI-V150 上是「显式 smem / tile / 软件 pipe 的 Triton 扩展」，**不是** Hopper WGMMA/TMA/mbarrier 兼容层。优化候选只取下面标为**已验证**的项；API 能 import、白名单有名字，都不等于可用。

```python
import triton.experimental.tle.language as tle
# 常见门控：has_triton_tle(3, 6, 0) → True（本机 FlagTree/Triton 3.6）
```

探测环境（2026-10-13）：FlagTree `0.6.2a3+iluvatar3.6`，Triton 3.6.0，PyTorch 2.7.1，CoreX/Driver 4.4.0，GPUTarget `corex/arch=71/warp_size=64`。下列结论均来自本机最小 `@triton.jit` 核：API 检查 → 编译 → 正确性；同步 / pipe / wgmma 类核用独立进程并设超时。

**探测规模（闭合）：** 共 34 项原语/变体探测，其中 **17 项** 形成可复用正确实现（含对照基线 `tl.dot`）；其余 **17 项** 为 UNSUPPORTED / COMPILE_FAIL / API_MISSING，名单见下表。只把 SUPPORTED / SUPPORTED_PARTIAL 放进优化候选。

#### 7.1 命名空间与白名单

| 事实 | 说明 |
| --- | --- |
| 真实路径 | Lite 在 `tle.*`（`load` / `extract_tile` / `insert_tile` / `pipe`）；Struct/Sync/MMA 在 `tle.gpu.*`。不要假设全在 `tle.gpu` |
| 活跃前端 | 安装包内 Iluvatar `code_generator` **不**调用 `_require_tle_primitive`，白名单不会在调用前拦截 |
| 白名单声明 | 后端 `TLE_SUPPORTED_PRIMITIVES` 列出：`extract_tile`、`insert_tile`、`cumsum`、`pipe*`、`gpu.alloc` / `copy` / `local_ptr` / `memory_space` / `warp_specialize` |
| 解析坑 | `primitive_name()` 会把 `pipe.reader` 收成 `reader`，与真实调用名对不齐。**以编译 + 正确性为准** |
| 语言层另有 | `tle.load`、`tle.gpu.wgmma` / `wgmma_wait`、barrier、`set_layout`、encoding 类。存在 ≠ 降得下去 |

| 原语 | 状态 | 失败要点 |
| --- | --- | --- |

| 对比 | 候选 vs 基线 | 加速比 | 结论 |
| --- | --- | --- | --- |
| `alloc`+`local_ptr` 往返 vs 直接 load/store | fp16 64×128：3.59 vs 2.86 µs | ≈0.80 | 显式 smem **正确但无搬运加速** |

#### 7.4 适用场景与写法

**可以写进候选**

1. 显式 smem tile：`tle.gpu.alloc(..., scope=tle.gpu.smem, nv_mma_shared_layout=False)`，再 `local_ptr` 或 `copy`。适合需要手工 staging 的路径；不要预期比直接 `tl.load`/`tl.store` 更快。
2. 矩阵计算继续用 **`tl.dot`**；必要时在匹配的 operand load 上用 `stride=` 提供真实行跨度，按 [SME 触发矩阵](#v150-sme-triggers) 核对最终指令，不把它当通用二维 load 开关。不要用 `tle.gpu.wgmma`。
3. `tle.pipe` 仅作 capacity=1、同 CTA 顺序 producer/consumer 的软件同步骨架；`has_mbar=0`，不能当硬件双缓冲流水。
4. `insert_tile` / 小 tile `extract_tile` 可用于寄存器块拆装；大 tile 先对拍。

**最小可用样例（已验证）**

```python
@triton.jit
def smem_roundtrip(x_ptr, y_ptr, M: tl.constexpr, N: tl.constexpr):
    offs = tl.arange(0, M)[:, None] * N + tl.arange(0, N)[None, :]
    vals = tl.load(x_ptr + offs)
    buf = tle.gpu.alloc((M, N), dtype=vals.dtype, scope=tle.gpu.smem, nv_mma_shared_layout=False)
    ptr = tle.gpu.local_ptr(buf)
    tl.store(ptr, vals)
    tl.store(y_ptr + offs, tl.load(ptr))
```

```python
# pipe：capacity 与 field 第 0 维一致；同 CTA 内顺序 acquire→copy→commit→wait→load→release
channel = tle.pipe(capacity=1, scope="cta", data=buf)  # buf shape (1, M, N)
slot = channel.writer().acquire(0)
tle.gpu.copy(x_ptr + offs, slot.data, (M, N))
channel.writer().commit(0)
ready = channel.reader().wait(0)
out = tl.load(tle.gpu.local_ptr(ready.slot.data))
channel.reader().release(0)
```

#### 7.5 不要做的事

- 不要把 N 卡 `tle.gpu.wgmma` + `nv_mma_shared_layout=True` + TMA/mbarrier 原样搬上天数。
- 不要用 `alloc_barrier(s)` / `barrier_*`；builder 没有对应 op。
- 不要把 `warp_specialize` 当可用路径；当前编译直接失败，不是「降到软件 barrier 就能用」。
- 不要用 `set_layout` / encoding 类做显式布局调优；缺 `ensure_ttg_layout_attrs`。
- 不要用 `tle.load(is_async=True)` 替换已能走 SME 的 `tl.load`。
- 不要把 `HAS_TLE_*` 理解成「同一份核，关 TLE 指令」。GDN2 关了就换整段实现。
- 未确认支持前，不要对 pipe / barrier / warp_specialize / wgmma 做大规模性能扫描。

### 8. 编译管线与 IR

#### 8.1 阶段

```text
Python @triton.jit
  → TTIR     make_ttir（含 rewrite tensor pointer；sm71 还会把 tensor descriptor 改成 pointer）
  → TTGIR    make_ttgir（coalesce、accelerate_matmul、SME load、pipeline(num_stages)、TLE barriers…）
  → LLIR     make_llir（分配 smem、降到 LLVM、warp_specialize_to_llvm）
  → ASM      仅 ivcore11 可打印
  → cubin    iluvatar.translate_llvmir_to_cubin
```

kernel 调用约定：`iluvatar_kernel`。`maxnreg>0` 时变成函数属性 `iluvatar-num-vgpr`。

#### 8.2 调试编译

| 环境变量 | 作用 |
| --- | --- |
| `TRITON_KERNEL_DUMP=1` | 把各阶段 IR dump 到 `TRITON_DUMP_DIR`（默认 `~/.triton/dump`） |
| `TRITON_ALWAYS_COMPILE=1` | 跳过 cache |
| `TRITON_PRINT_AUTOTUNING=1` | 打印 autotune 选择 |
| `TRITON_DISABLE_SME=1` | 关掉 SME load |
| `TRITON_OVERRIDE_ARCH=sm71` | 强制 arch（一般不用） |
| `TRITON_DEBUG=1` | 打开 debug |
| `TRITON_DISABLE_LINE_INFO=1` | 减小二进制、加快编译 |

看资源：kernel 对象上的 `n_regs`、`n_spills`、`shared`（load cubin 时 `cuFuncGetAttribute`）。`n_regs` 是该 kernel 的每线程向量寄存器分配量；256 是已观察到的高压点，不作为通用硬上限；`shared` 是每 block 共享内存字节数。两者的 SM 级池子和换算见 4.2。`n_spills` 是 local memory 字节数 / 4，即 32-bit 个数。

超共享内存的报错长这样：

```text
OutOfResources: shared memory, Required: 132100, Hardware limit: 131072
```

这是编译期失败。spill 导致的是运行时：

```text
RuntimeError: Triton Error [CUDA]: out of memory
```

两者不要当成同一种 OOM。后者要看 `n_spills × 线程数 × grid`。

#### 8.4 能力触发的确认与 SDK 声明边界

能力确认按下面顺序进行，不把不同证据混成一个支持结论：

1. **表达层**：记录 API、dtype、tensor rank、stride、对齐、mask、消费者、launch 参数与环境开关。更换这些条件可能选择不同编译路径。
2. **IR 层**：Triton 看 `kernel.asm["ttgir"]`、`["llir"]` 与 metadata；候选位图、类型转换和 intrinsic 声明不等于最后已执行相应机器指令。
3. **机器指令层**：Triton 看 `kernel.asm["asm"]`；C++ 可对已编译 binary/fatbin 使用 `ixobjdump --dump-sass`。汇编文本的 `ml_* / sl_*` 与反汇编的大写名字属于不同表示方式。
4. **功能层**：完整对拍，并覆盖实际 tile、尾块与数值范围。编译成功但数值错误的路径不能进入性能比较。
5. **性能层**：检查资源、动态计数与无 profiler 时间。专用指令可能被转换、重排、同步或驻留下降抵消；有指令不等于已提速。

本次 `ixobjdump --dump-sass` 虽正常返回，也存在部分指令地址没有输出助记符的情况，不能把未显示当作不存在。INT8 dot4 的证据保留为已运行的 C++ 接口、`llvm.bi.idot4` 和正确性；不补造缺失机器助记符或每周期吞吐。

**SDK 声明的边界**：已扫描安装版 `llvm/IR/IntrinsicImpl.inc` 等文件，提取出 547 个 `llvm.bi.*` 名称，其中有更多 matrix、SME、SMEX、TMA、WGMMA、barrier 与 async-copy 声明。它们跨多代目标，547 不是 V150 可执行指令数，更不能从声明直接认定本卡可用。当前高层 TLE 的 WGMMA/相关 barrier 仍按已有失败记录处理。

**本轮探针范围**：16 项 Triton 普通算术/整数/转换，10 项 CoreX C++ 接口，12 项独立进程 SME 触发组合，6 项统一值/原子语义，共 44 个功能配置。42 个通过，2 个明确失败分别是 `dp2a_lo` 编译失败与所测 FP16 load→FP32 cast→dot 数值失败。除此以外的 SDK 声明没有被扩写成已确认硬件能力。（2026-10-15）

#### 9.4 计时注意

1. 先 `synchronize` 再读 Event。
2. autotune / 编译不要算进稳态时延。SageAttention 第一阶段墙钟 19 小时，表上却是毫秒～百毫秒，差在 `static_range` 编译。

4. 对比 N 卡数字时核对：B/H/D/dtype、是否 FP8 MMA、是否 WGMMA、以及 TFLOPS 公式是否同一套。

#### 9.5 ixkn 指令构成：ALU / SFU / BFU / TCU

`ixkn-cli` 的 Executed Instructions 里，和计算管道相关的字段大致是：

| 字段 | 含义 |
| --- | --- |
| Single-Lane ALU / Control Flow | 标量侧。循环下标、整组线程相同的控制流 |
| Multi-Lane ALU Integer / Half / Single Float | 向量 ALU |
| `+BFU Instructions` | 见 [4.6](#v150-compute-pipelines)。纯拷贝也可有大量计数，不能直接用作 `exp2` 数量 |
| `+SFU Instructions` | 实测 `exp2`、`sqrt`、`rsqrt`、倒数；按具体生成指令判断，不代替高层函数调用次数 |
| `+Multi-Lane Matrix Instructions` | TCU / `tl.dot`；计数不直接等于模型 FLOPs 或硬件峰值 |
| Multi-Lane Global / Shared / SME Memory | 访存，不是计算管道 |

采集仍用 `ixkn-cli`（见 9.3）。对比两次报告时固定 shape、dtype 和 kernel 名；profiler 会改时序，加速比仍以无 profiler 的 `do_bench` 为准。


#### 9.6 ixKN CLI 采集方法与指标边界

`ixkn-cli` 是 IXplorer Kernel Analyzer 的命令行工具。BI-V150 / CoreX 4.4.0 环境下已验证版本为 4.4.0。

查看能力：

```bash

```

常用 Section：

| Section | 主要用途 |
|---|---|
| Memory | 全局/共享内存、缓存、带宽、bank conflict |
| Instruction | 动态指令数量和类型 |
| SpeedOfLight | 计算与访存资源使用概况 |
| Occupancy | 理论与实际 occupancy、资源限制 |
| LaunchStats | grid/block、寄存器、shared memory 等 launch 信息 |
| WarpStateStats | warp 状态与停顿 |

`default` 采集 5 个 Section、约 89 项；`detailed` 和 `full` 采集 8 个 Section、约 122 项。指标越多，kernel replay 越多，采集开销也越大。

推荐的最小化采集模板：

```bash

  --section Memory,Instruction,SpeedOfLight \
  -k '<kernel名称或正则>' \
  -s 5 \
  -c 1 \
  ./<程序> <参数>
```

参数含义：

- `--section`：只采需要的分析模块，减少 replay 和噪声。
- `-k`：按 kernel 名称或正则过滤，避免把初始化和其他 kernel 混入。
- `-s 5`：跳过前 5 次匹配 launch，避开预热。
- `-c 1`：只采随后 1 次匹配 launch。
- `--csv`：输出 CSV，便于做固定字段对比。
- `-o`：导出可重新加载的 profile。
- `--replay-mode kernel`：按 kernel 重放，默认行为。

#### Replay 对计时的影响

ixKN 为采集多个硬件指标会重放 kernel。应用程序内部的 CUDA Event 会把 profiler 干扰算进去，因此 profile 期间程序自己打印的平均时间不能作为生产性能。

Global Memory 实测中：

| 模式 | 无 profiler 的 CUDA Event | ixKN Duration | profile 期间程序内平均时间 |
|---|---:|---:|---:|
| Stride=1 | ≈116 μs | 111.576 μs | ≈2.94 ms |
| Stride=16 | ≈1149 μs | 1160.65 μs | ≈23.04 ms |

使用规则：

- 生产性能和加速比：使用无 profiler 的 CUDA Event 或 `do_bench`。
- 单次 kernel 行为：使用 ixKN Duration 和硬件计数器。
- 不要使用 profile 期间应用程序内部累计出来的平均时间。
- 两份 ixKN 报告对比时固定 shape、dtype、kernel 名、warmup、采集 Section 和过滤规则。

#### Memory 与 Instruction 字段怎么读

| 指标 | 可用含义 | 不应直接推断 |
|---|---|---|
| Global Memory Instructions | 动态执行的全局访存指令数 | 实际 HBM 字节数 |
| L1/L2 Cache Hit Rate | ixKN 定义下该层级请求的命中比例 | 两级命中率可相加、cache line 大小 |
| L2 Cache to Memory Access | L2 向后端内存路径发出的请求统计 | 与 NVIDIA sector/DRAM transaction 一一对应 |
| Global Memory Load/Store Throughput | ixKN 定义的内部吞吐指标 | 程序有效带宽或物理 HBM 带宽 |
| Logical Bandwidth | 程序有效读写字节数 ÷ 无 profiler 时间 | 硬件内部搬运总量 |
| LSU Utilization | load/store 执行资源活跃程度 | 已达到 HBM 峰值 |
| Multi-Lane ALU Instructions | 向量算术、整数下标和地址计算等动态计数 | 模型 FLOPs |
| Matrix Instructions / TCU Efficiency | 矩阵路径是否执行及其利用情况 | 普通 ALU 或访存效率 |

纯访存 kernel 也会产生大量 Multi-Lane Integer ALU，因为线程索引、地址计算和边界判断都走 ALU；因此 ALU 指令数不能直接等同于浮点工作量。对 ixKN Request、Throughput 等字段，在缺少正式公式时不要套用 NVIDIA Nsight Compute 的 Sector、DRAM Bytes 口径。


#### 9.7 CUDA Graph 短 Kernel 稳定计时

短 kernel 使用普通 CUDA Event 连续计时时，可能出现较大波动；本次 1024³ GEMM 的 BF16 曾在不同运行中出现约 79～254 μs。测试卡观察时基本空闲，但运行期间时钟状态未完整记录，因此不能把波动简单归因于其他进程、缓存或频率。

已验证 CoreX PyTorch 支持 CUDA Graph capture、replay 和正确性校验。对固定输入、固定地址、无动态控制流的短 kernel，可采用：

1. 完成编译，并执行足够的普通预热。
2. 在一张 Graph 中捕获多次 kernel，摊薄单次 replay 和 Event 开销。
3. 对 Graph replay 再预热。
4. 用 CUDA Event 测多次 replay 的总时间。
5. 总时间除以 `每张 Graph 的 kernel 次数 × replay 次数`。
6. 改变精度或候选顺序时同时跑正序和逆序，检查顺序偏差。

本次稳定方案使用 20 次编译后预热、每张 Graph 捕获 20 个 GEMM、10 次 replay 预热和 100 次正式 replay。CUDA Graph Benchmark 与 ixKN 采集必须分开：Graph 用于无 profiler 的稳定性能，ixKN 用非 Graph 单 kernel 采集指令和资源；不能把 ixKN replay 期间的 CUDA Event 时间用于计算 TFLOPS。

使用限制：

- Graph API 存在不代表特定 kernel 一定可 capture，必须验证 capture、replay 和结果正确性。
- Graph 会固定地址和 launch 结构，不适合直接代表动态 shape、动态分配或控制流频繁变化的真实调用。
- Graph 改善的是计时稳定性和 launch 摊销，不证明 kernel 本体计算更快。
- 最终报告必须注明是否使用 Graph、每次 Graph 内的 kernel 数、replay 次数、shape、tile、dtype 和吞吐公式。

#### 9.8 多 stream 与 Graph 的实测边界

**是什么：**多 stream 和 Graph 是使用硬件执行资源的运行时入口；接口存在与任务实际重叠是两个问题。

本次使用两个独立、各一个 CTA 的长计算 kernel，11 次计时，计算结果通过 `atol=rtol=1e-6` 校验：未捕获 Graph 时，串行两个任务约 1.56 ms，两个 stream 约 1.60 ms，**该配置没有测到并发收益**。不能据此推出芯片完全不支持 concurrent kernel。

单 stream Graph 可运行；所测双 stream fork/join 捕获在当前软件栈报 `capturing stream has unjoined work`。

**怎么用：**小任务优先把单 kernel 的 grid 与工作分配做好。需要多请求重叠或跨 stream Graph 时，先验证对应执行图和时间线，不把“用了两个 stream”计作已获得硬件并发。

实验细节：各 kernel 为 `grid=1, block=256`，对独立输出执行 262144 轮有数据依赖的 FP32 recurrence；输入与 CPU 参考固定，禁用浮点融合选项，最大绝对误差 2.3842e-7。11 次 CUDA Event 中位数：未捕获 Graph 的串行两任务 1564.096 µs、双 stream 1596.615 µs；单 stream Graph 的单任务 810.500 µs、串行两任务 1473.596 µs。不同模式的频率/时序可能变化，不根据单任务时间直接反推重叠比例。双 stream 捕获使用 fork/join 依赖，报错发生在 capture_end；另起进程进行未捕获 Graph 的功能和时间验证。

**状态**：单 stream Graph 和普通双 stream 调用已验证正确；所测双 stream Graph 捕获明确失败；当前配置的并发收益未成立。不推断所有多流图、其他版本或硬件物理并发能力都不可用。（2026-10-15）

### 10. 优化手段（按收益和风险）

下面只列在 BI-V150 上验证过或明确失败过的手段。新手段先标状态再进表。

#### 10.1 先保证能编、能 launch

1. **共享内存压到 128 KiB 以下**  
   降 `num_stages`、减小 `BLOCK_M/N/K`、不要多 buffer。MSA 把 page 内计算 tile 从 128 降到 32（`_PREFILL_DIRECT_BLOCK_SIZE_K = 32`），选择语义仍是 128 token 一块。
2. **看 `n_spills`**  
   spill≠0 时，grid 一大就会 launch OOM。FP8 MMA、过大 TILE、过多 live accumulator 都是来源。目标是 **0 spill**。MSA 改 dequant+bf16 后 `n_spills` 295→0，`n_regs` 256→199。
3. **不要 `static_range` 按问题规模展开**  
   改 `while` + 基地址寻址。编译从 10 小时降到分钟级。
4. **不要用 NVIDIA SM 门槛拒绝功能**  
   FP8 存储、TLE 是否存在、PDL 是否存在，分别探测。

#### 10.2 计算

| 手段 | 适用 | 说明 |
| --- | --- | --- |
| `tl.dot` 走 TCU | f16/bf16/f32/i8 | 主路径。K 维对齐 16/32 |
| INT8 量化 + scale | SageAttention / GEMM | 可进入 Matrix 路径，但 tile 正确性必须逐项校验；当前通用 GEMM 仅验证 `32×32×32` |
| FP8 **存储** + bf16 计算 | 带宽敏感路径 | 必须把解码成本计入；独立 decode 与当前融合 GEMM 反例均比 BF16 慢，只有端到端实测更快才保留 |
| FP8 **MMA** | 仅小核实验 | bench 规模放弃 |
| 融合 kernel | GDN2 | intra / WY / gate 融进少量 kernel，相对 Torch 朴素 6×–22× |
| Neumann 近似求逆 | GDN2 BT=16 | 用一串 `tl.dot` 代替精确三角求解；误差仍低于 0.01 RMSE |
| 拆 K（flash-decoding） | MSA decode | query 只有 1 token 时 parallelize 在 KV block 上 |
| 小 tile 换占用 | MSA prefill | 32 的 K tile 换 smem/寄存器，正确性不变 |

#### 10.3 访存

| 手段 | 说明 |
| --- | --- |
| SME 自动/显式 stride | 同时核对 host tensor 元数据、dot 消费者、布局与真实行跨度；结果以 [SME 触发矩阵](#v150-sme-triggers) 和机器指令为准 |
| `tle.load(is_async=True)` | 仅打 TTIR async 属性；asm 同步退化，相对 `tl.load` 无收益甚至更慢。详见 [7.3](#73-性能小核cuda-event2026-10-13) |
| `num_stages` software pipeline | smem 够才有意义；V150 经常不够 |
| 双缓冲 KV | MSA 只对最小 GQA tile 开 64-token double buffer；更大 tile 复用单页 staging，否则 barrier/softmax 开销吃掉收益 |
| 不要物化 `T×T` | SageAttention Torch 对照从 4096 起 OOM，改成 KV tile + online softmax 才能跑到 32768 |
| FP8 KV | 仅在端到端计时获益时保留；输入减半可能被 decode、布局转换、shared-memory 和寄存器开销抵消 |

#### 10.4 Launch / 并行

| 手段 | 说明 |
| --- | --- |
| `num_warps=4` | 默认、最稳 |
| `do_not_specialize_on_alignment` | 减少无意义重编译 |
| 关掉会改 BLOCK 的 autotune 调整 | `adjust_block_size=False` |
| 不传 `maxnreg` | 避免错误占用模型 |
| 不传 `launch_pdl` / `num_ctas>1` | 当前目标的门控/后端不支持，不用该失败推断完整物理架构 |

##### 任务颗粒度与尾波

**SM 级颗粒度：**设备只有 16 个 SM，需要同时考虑每个 SM 能驻留多少个 block。以每 SM 只能驻留一个 block 为例，17 个等长 block 会形成一个完整波次和一个仅有一个 block 的尾波。小 batch decode 或窄矩阵可尝试沿 token/head、输出维或 K 维增加并行；split-K 还需要计入合并、原子更新或额外输出的成本。

上述例子是已知 16 SM 与指定驻留条件下的资源推导，用于决定要测试的任务分块；不代表排序、split-K 或增加 warp 数已经证明有收益。小 batch decode、窄矩阵、单 head、少量专家都应检查 grid 数与尾波。

#### 10.5 明确无效或未做的

- N 卡 WGMMA + TMA prefill：编不过。`wgmma` 还要求 `nv_mma_shared_layout`，和 Iluvatar alloc 互相锁死。
- 把 H100 的 `--maxnreg` 抄过来。
- 在天数上开 `STATIC_KV` 换「编译期展开换运行时」。编译会先把你拖死。
- 依赖 `tl.range` 遍历动态 KV。
- 用 capability (7,1) 推断「没有 Tensor Core / 没有 FP8」。
- 把软件多项式 `2^x` 替代特殊函数当成默认提速手段。2026-10-15 受控探针已确认所测 `exp2` 计入 SFU，见 [4.6](#v150-compute-pipelines)；本机未验证多项式替代的精度与端到端收益，不作为已验证优化。
- 自研 TLE MMA 布局：未实现。2026-09-18 / 2026-10-13 探测确认：矩阵替代物是 TCU `tl.dot` + SME，不是 `tle.gpu.wgmma`。
- `tle.gpu.alloc_barriers` / Hopper mbarrier：builder 没有 `create_barrier_alloc`。
- `tle.gpu.warp_specialize`：编译死在 `ConvertTritonToTritonGPU`，不是可用的软件 barrier 降级。
- 指望 `tle.load(is_async=True)` 加速：asm 同步退化，相对 `tl.load` 加速比小于 1（见第 7 节）。

### 11. 迁核检查清单

从 N 卡 / 昇腾 / 其它后端往 `_iluvatar` 搬时按这个过：

1. **代码只进** Iluvatar 后端目录（项目内 `_iluvatar/`），不改 N 卡原包。

## 6. 厂商库

### 13. 厂商库 IxFormer

范围：查本机已装 IxFormer 有没有 MiniMax 式 block-sparse Attention；**没有改** FlagAttention / Baseline 代码。  
包：`ixformer 0.7.0+corex.4.4.0`（`git_commit=0483ee134eea`，配套 `torch 2.7.1+corex.4.4.0`）。探测日期 2026-09-18。

#### 13.1 能力边界

本机版本为 `ixformer 0.7.0+corex.4.4.0`，配套 `torch 2.7.1+corex.4.4.0`。能力判断以本机实际导出的接口和运行结果为准：支持 Flash、Paged、MLA、滑窗、量化和 MoE；不提供 MiniMax M3 所需的 per-head top-k block-sparse Attention，也不提供带任意 bias/mask 的 Flash Attention。

#### 13.2 一句话

本机 IxFormer 是 **厂商 CUDA 注意力/量化/MoE 库**，不是 Triton DSL。  
注意力侧有 Flash / Paged / MLA / 滑窗；**没有** MiniMax MSA 那种「每个 kv-head 各自 top-k 页」的稀疏核。  
要做 block-sparse，只能把 top-k 页 **重映射进 `block_tables`**，再调 `vllm_paged_attention`（Baseline 已经这么干）。

```python
from ixformer import vllm_paged_attention, flash_attn_func, paged_attention
```

#### 13.3 本机默认走哪条核

`ixformer.core.config`：

| 环境变量 | 本机默认 | 作用 |
| --- | --- | --- |
| `IXFORMER_PAGED_ATTENTION_ALGO` | **`ixinfer`** | `vllm_paged_attention` 绑到 `vllm_paged_attention_ixinfer`（`ops.infer.vllm_paged_attention`） |
| 同上设成 `ixformer` | — | 改绑 `paged_attention()`（`ops.infer.paged_attention`，HND/NHD/STD） |
| `IXFORMER_UNPAD_ATTENTION_ALGO` | `ixinfer` | unpad Flash；可选 `ixinfer-ex` |
| `IXFORMER_USE_TORCH_OPS` | False | True 时走 `torch.ops._C` |
| `IXFORMER_FLA_ENFORCE_TRITON` | 0 | GDN recurrent 强制 Triton 路径 |

没设环境变量时：

```text
from ixformer import vllm_paged_attention
# == vllm_paged_attention_ixinfer
```

未设置环境变量时，导入的 `vllm_paged_attention` 就是这条默认核。

#### 13.4 和 MSA 相关的注意力接口

##### `vllm_paged_attention`（默认，ixinfer）

这是 **decode / 短 query 读 paged KV** 的主入口。query 一条 token 一行；`block_tables[i]` 是第 i 条序列要 attend 的物理页。

```text
output, query:     [num_tokens, num_heads, head_size]     fp16 / bf16
key_cache/value:   [num_blocks, num_kv_heads, block_size, head_size]
block_tables:      [num_tokens, max_num_blocks_per_seq]   int64
context_lens:      [num_tokens]                           int32
```

其它参数：`num_kv_heads, scale, block_size, max_context_len`；可选 `alibi_slopes, softcap, causal=True, window_left/right=-1, use_cuda_graph, sinks`。

**没有** `attn_bias` / 任意 mask / per-head 不同页表。一条序列的所有 head 共用同一张 `block_tables[i]`。

可用变体：

| 函数 | KV | 备注 |
| --- | --- | --- |
| `vllm_paged_attention_int8` | Q/K/V 都是 int8 + scale | |
| `vllm_paged_attention_mix` | Q/K int8，V 仍 fp16/bf16 | |
| `vllm_paged_attention_mla` | 压缩 KV：`[num_blocks, block_size, kv_lora_rank+qk_rope_head_dim]` | DeepSeek MLA |
| `vllm_paged_attention_mla_fused` | Q 拆 `q_nope` / `q_pe`，可顺带写 cache | |
| `vllm_paged_attention_v4` / `v5` | 旧布局 | |
| `paged_attention_v7`（tgi） | 调同一套 ixinfer paged | |

INT8 变体是 **per-token / per-block 的 QK 量化 paged**，不是 MiniMax 的 FP8 KV + top-k 稀疏。

##### `paged_attention`（algo=`ixformer`）

```text
kv_cache_format:
  STD  与 vLLM 默认相同
  NHD  一页内 [block_size, num_kv_heads, head_dim]
  HND  一页内 [num_kv_heads, block_size, head_dim]   # 默认
algo: -1 按 format 自动选；0 / 1 指定 kernel
```

可带 `key_cache_scales` / `value_cache_scales`。  
`paged_attention_flashinfer` 用 indptr + indices；`batch_paged_attention` 只要 HND，且要 CPU 侧 `q_index` / `kv_index`。

##### Flash Attention（稠密，无 bias）

`flash_attn_func(q, k, v, dropout_p=0, softmax_scale=None, causal=False)`

- 输入 `[B, S, H, D]` fp16/bf16，GQA 可以
- **不支持 training、不支持 `return_attn_probs`、没有 attn_bias**
- 内部 pad 到 `head_dim % 32 == 0`，再走 `ixinfer_flash_attn_unpad`
- `flash_attn_varlen_func` 用 `cu_seqlens_*`；同样没有任意 mask

所以 **不能** 拿 Flash + bias 当 MSA 稀疏核。Baseline 实测过：ixattnbkd 不吃 fp32 bias。

##### 本机 **没有** 的东西

对本机导出接口和实现符号检查后，与 `sparse` / `topk` / `indices` 有关的能力只有：

- MoE：`moe_topk_softmax`、`moe_grouped_topk`、token 重排
- Paged KV 的 `block_tables` / `paged_kv_indices`
- FLA 的 `ssm_state_indices`
- `bnb_double_quant.COOSparseTensor`（量化稀疏，不是 attention）

**没有** `sparse_attn` / `block_sparse` / MiniMax indexer + top-k GQA。

`indexer_k_cache(key, kv_cache, slot_mapping)` 只是把 K 按 slot 写入 `[num_blocks, block_size, head_dim]`，不是 index-score。

#### 13.5 用 paged 核冒充稀疏（已验证路径）

天数 paged 核的语义是：**每条 query 序列一张页表，attend 这些页上的 KV**。  
MSA 的 top-k 是 **每个 (token, kv-head) 不同页**，所以要重映射：

1. 每个 `(query token, kv-head)` 当成一条 decode 序列
2. 该 head 的 top-k 逻辑块 → 物理页，按 block id **排序**（只有最后一页可以是半页，才能用 `context_lens` 截断）
3. 虚拟页号 = `phys * Hkv + head`，K/V reshape 成 `[P * Hkv, 1, page, D]`
4. 调 `vllm_paged_attention`

该重映射路径已通过正确性与性能测试。

实测约束：

- `context_lens < 2`（prefill 第一个 token）厂商核数值不对，要 torch 回退
- Prefill `n_tok >= 512` 按 kv-head 分次 launch，比一次 flatten 成 `N * Hkv` 条更快
- Decode 小 batch 可以 flatten
- 8K prefill：IxFormer attn ≈ 69 ms；index 仍是 torch fp32 GEMM ≈ 40 ms

#### 13.6 其它和现有算子相关的接口

| 需求 | IxFormer 里有什么 | 能不能直接当 FlagAttention 核 |
| --- | --- | --- |
| SageAttention（QK INT8 per-block + smoothing） | `ixformer.contrib.sageattention.sageattn`：整段 Q/K 量化成 int8，V 仍 fp16，走 int8 FMHA；`is_causal` 的 int8 路径直接 `NotImplementedError` | **不能**。不是 FlagAttention 那套 |

| GDN / gated delta | `fused_recurrent_gated_delta_rule`：厂商 CUDA，**只支持 K=V=128**；`IXFORMER_FLA_ENFORCE_TRITON=1` 才走包内 Triton | FlagAttention GDN2 仍用自己的 Triton |

#### 13.7 KV cache 布局（写重映射时用）

支持三种 KV cache format：

```text
STD  K: [num_blocks, num_kv_heads, head_size/x, block_size, x]
     V: [num_blocks, num_kv_heads, head_size, block_size]
NHD  [num_blocks, block_size, num_kv_heads, head_size]
HND  [num_blocks, num_kv_heads, block_size, head_size]   # paged_attention 默认
```

`vllm_paged_attention_ixinfer` 文档写的是 **HND**：`[num_blocks, num_kv_heads, block_size, head_size]`。  
Flash 侧 `head_dim` 不是 32 倍数会 pad。

写 cache：`reshape_and_cache_flash` / `_int8` / `_mix`，以及 `paged_attention_cache_appended`。

#### 13.8 对后续工作的含义

1. **不要再找 IxFormer 的 MiniMax sparse kernel**——本机 0.7.0 没有。
2. 对比基线继续：Torch 做 index/topk，IxFormer paged 做稀疏 attn。
3. FlagAttention 优化核继续自己写 Triton；厂商库替代不了 per-head top-k 的数据流。
4. `flash_attn_func` 只适合稠密 causal/non-causal；带 mask 的 SDPA 在这张卡上极慢，不要用。
5. 公开 C++ `xllm_paged_attention` 和本机 Python `vllm_paged_attention_ixinfer` 是同一类核（block_tables + context_lens + window/softcap）。第三方 mojo_opset 的 GQA/SWA 包装也是它，不是另一套稀疏算法。

## 7. 算子与索引

### 14. 算子沉淀（平台相关）

本节直接记录下次迁核需要复用的实现选择、正确性、性能结果和失败边界。

#### 14.1 GDN2（`chunk_gdn2`）

- 优化核被 `if HAS_TLE_GDN2:` 包住，但核内几乎是普通 Triton（`make_block_ptr` + `tl.dot` + 少量 inline asm）。
- 公开入口 `chunk_size=16`；naive Triton 是 `BT=64` 多核路径；Torch 朴素版在 `iluvatar_naive`。
- Intra autotune：`BK/BV ∈ {16,32,64}`，`num_warps ∈ {1,2,4}`，`num_stages ∈ {1,2,4}`。H/O 当前是 c005：`BV ∈ {32,64,128}`，`warps ∈ {2,4}`，`stages ∈ {1,2}`。
- 相对原始 fused，官方 24 项全赢，最好一档约 1.66×（降时 39.7%）。相对 Torch 朴素大约 6×–22×。正确性 48 passed（含 native 对照）。
- 冷启动 pytest / 官方 bench 各约 1.5 h；热启动各约 6 min。不要为冷启动去砍官方 autotune。

#### 14.2 MSA（MiniMax M3 paged sparse attention）

- Prefill **一律** `_gqa_sparse_fwd_direct`，`num_warps=4`，`num_stages=1`，`BLOCK_SIZE_K=32`。
- FP8：存储打开；计算 = load 后 `.to(q.dtype)` × scale，bf16 `tl.dot`。
- Decode 算法未改；`arch=71` 不开 PDL。
- Index topk 在有 TLE 时可以走 radix；本机跑过。
- 正确性 25 passed。Prefill 相对 Torch 约 2.5×–3.3×；decode 大 batch 可到 15×–40×。
- Prefill 仍是秒级，这是 portable 核的水平，不是 N 卡 WGMMA。

#### 14.3 SageAttention

- 源是昇腾 TLE 核，不是 N 卡 WGMMA。
- `tle.load(is_async=True)` + INT8 QK + online softmax 可用，但 async 路径无硬件收益（见 [7.3](#73-性能小核cuda-event2026-10-13)）；能走 SME 的地方优先 `tl.load`。
- 必须关掉 `STATIC_KV`，内层改 `while`。否则编译墙钟不可接受。
- 量化 scale 按 **64 行一块**；autotune `BLOCK_N=32` 时要用 `start_n // K_SCALE_BLOCK`，不能每 tile `scale_ptr += 1`。
- 稳态大约 2.7–3.0 TFLOPS。32768 仍可能 autotune launch OOM。
- 不要传 `--maxnreg`。

## 8. TLE 显式 Shared Layout 与后端边界专项

### 5. TLE 显式 Q shared layout：实测 bank conflict 对照

显式 Q shared-memory 探针的三种 `max_phase` 均在 QK 形状
`[8,64] x [64,32]` 上通过正确性验证。随后将各自 **实际生成的 LLIR Q-buffer
读写地址表达式** 原样复现到独立的 C++ shared-memory 探针中，
并在 BI-V150 以 grid `(8192,1,1)`、block `(128,1,1)`、64 次迭代、6144 B 动态
shared memory 采集 ixKN 结果。三组均 `validation=passed`，寄存器均为 scalar
10 registers/warp、vector 12 registers/thread，local memory 均为 0 B/thread。

| TLE `max_phase` | shared-store conflict | shared-load conflict | ixKN duration | CUDA event elapsed |
|---|---:|---:|---:|---:|
| 1 | 0 | 0 | 158230 ns | 11.025596 ms |
| 2 | 8,388,608 | 131,072 | 167980 ns | 10.058942 ms |
| 4 | 8,388,608 | 131,072 | 167980 ns | 11.035519 ms |

按本次 grid 和迭代数归一化，phase 2/4 的 shared-store conflict 为每 block 每轮
16；shared-load conflict 为每 block 16。phase 1 的两项均为 0。

LLIR 地址式解释：

- phase 1：Q 写入为连续的 32-bit 向量写，地址为 `(threadIdx.x << 2) & 508`，
  及其 `+512` 分区；
- phase 2：Q 写入为 `((threadIdx.x & 63) << 1) XOR wave_offset`，其中
  `wave_offset` 为 0 或 130；
- phase 4：在 phase 2 基础上增加 `XOR 260` 的另一分区。

结论：BI-V150 并非所有 BF16 QK 的 shared 写都必然发生 bank conflict。同一个
`[8,64]` 显式 Q buffer，phase 1 可在真实硬件计数器上实现零 shared-store 与零
shared-load conflict；phase 2/4 则会产生冲突。因此 layout 是可操作的根因，后续
production 尝试应只以 phase 1 的显式 Q staging 为候选。上述 duration 仅用于这块
隔离 Q buffer 的方向判断，尚不代表完整 sparse-attention 的速度。

#### phase 1 接入 production 的反例（已回退）

曾将 phase 1 的两块显式 Q buffer 接入 D128 `SPLIT_D` 路径的 `q_lo/q_hi`，真实
`_gqa_sparse_fwd_direct` 在 `(1,8192,16,96)`、grid `(8192,16,1)`、block
`(128,1,1)` 上能够编译、发射并完成 profile；该实现随后已回退，不保留为候选。

实测资源为：shared-store conflict `192,413,696`、shared-load conflict
`416,808,960`、vector registers `108/thread`、动态 shared `6144 B/block`、
理论/实际 occupancy `25.00%/24.98%`、local memory `0 B/thread`。矩阵指令为
`473,956,352`。

结论：隔离 Q buffer 的 phase 1 虽然读写冲突均为零，但接入完整 attention 后改变了
QK 消费端的 shared load 路径，导致 production shared-load conflict 显著增加。
这证明“孤立 store 无冲突”不足以作为生产优化准入条件；必须以完整 kernel 的 store
和 load 两项计数共同判定。本候选在普通计时前即因资源门槛失败而回退。

#### `nv_mma_shared_layout` 不能作为 Q buffer 控制项

与 [7.2](#72-能力总表已验证--已证伪) 一致：当前栈上
`tle.gpu.alloc(..., nv_mma_shared_layout=True)` **直接失败**，报错
`iluvatar TLE alloc does not support nv_mma_shared_layout=True`。

`nv_mma_shared_layout=False` 的 phase 1 显式 Q buffer 可编译运行，TTGIR 为
`#ttg.swizzled_shared<{vec=1, perPhase=1, maxPhase=1, order=[1,0]}>`（无
`useTcu=true`），Q `local_load` 为 `dot_op(opIdx=0, useSme=0)`。

结论：该开关要么被拒绝，要么即便历史上曾被接受也**不会**把 Q buffer 变成 MMA/SME
专用 encoding。不能作为 production 的布局控制项；矩阵仍走自动 `tl.dot`。

#### `per_phase` 在 `max_phase=1` 下不改变 BI-V150 的实际地址式

对 phase 1 分别编译 `per_phase=1/2/4/8`，四组均通过正确性验证。TTGIR 的
`#shared1.perPhase` 字段会随参数变化，但从 LLIR 观察，Q buffer 的 store 和 load
地址计算、shared 指令序列以及矩阵指令完全相同；Q 写入仍为
`(threadIdx.x << 2) & 508` 及 `+512` 分区。

结论：当前后端在 `max_phase=1` 时没有把 `per_phase` 降为 Q buffer 的实际地址变化。
该参数已从探针删除，不能用于构造生产 Q staging 的 b4 映射。

#### `max_phase>1` 的 `per_phase` 组合：无写端收益

继续编译并验证 `p2_m2`、`p4_m2`、`p2_m4` 三种实际不同的 Q-buffer 地址式；三者
均正确。将其 LLIR 的 **store 地址式** 原样复现至独立 C++ shared-memory 探针，在 grid
`(8192,1,1)`、block `(128,1,1)`、64 次迭代、6144 B dynamic shared memory 上采集。

| 布局 | shared-store conflict | shared-load conflict | 每 block 每轮 store conflict | ixKN duration |
|---|---:|---:|---:|---:|
| p2_m2 | 8,388,608 | 131,072 | 16 | 168365 ns |
| p4_m2 | 8,388,608 | 131,072 | 16 | 168269 ns |
| p2_m4 | 8,388,608 | 131,072 | 16 | 168307 ns |

三者寄存器、shared 大小和指令规模相同，且都不优于此前 phase2/4 的 16 次写冲突。
结论：当前 TLE 暴露的 `max_phase/per_phase` 组合没有形成比现有布局更优的 BI-V150
Q staging 写映射，因此这些组合不应继续进入 production 候选。

### 6. CoreX shared 地址生成能力与边界

当前 Iluvatar Triton 后端声明支持 direct-to-LDS scattering：普通 async copy 会降低为 load 加 store，每个 lane 可以使用独立的 shared 地址。

结论：BI-V150/CoreX 当前后端具备 per-lane shared-store 地址能力；此前 Q staging
冲突不是硬件“不支持散射写”造成的，而是已生成的 lane→shared 地址布局造成的。因而
理论上可以实现 b4 这类地址扰动，但必须让 shared store 与 QK consumer 的 shared
local-load 使用同一套可逆映射。仅改变 store 地址会破坏读取布局，生产实测会转化为
大量 shared-load conflict（见第 5 节 production 反例）。

当前 TLE Python 接口已实测的限制：`max_phase`、`per_phase` 和
`nv_mma_shared_layout` 均不能生成所需的成对 b4 映射。**结论闭合：** 在当前已安装
Triton/CoreX 上，“手工 b4 映射”不是可用的生产手段；不要把它写成待验证候选。

### 7. TLE `shared_order=[0,1]`：实测为更差的写端布局

在相同的显式 Q buffer 形状 `[8,64]` 上，分别以
`swizzled_shared(order=[0,1], perPhase=1, maxPhase=1/2/4)` 编译、运行并通过正确性
验证。三组 LLIR 的 Q shared-store 地址式均已逐项复现到独立 C++ shared-memory 探针；测试
配置为 grid `(8192,1,1)`、block `(128,1,1)`、64 次迭代、6144 B 动态 shared memory。
三组均 `validation=passed`，资源相同：vector registers `12/thread`、local memory
`0 B/thread`、理论 occupancy `32.81%`（受 6144 B shared 限制）。

| `order=[0,1]` 的 `max_phase` | shared-store conflict | shared-load conflict | 每 block 每轮 store conflict | ixKN duration |
|---|---:|---:|---:|---:|
| 1 | 50,331,648 | 786,432 | 96 | 833711 ns |
| 2 | 50,331,648 | 786,432 | 96 | 836480 ns |
| 4 | 50,331,648 | 786,432 | 96 | 831615 ns |

结论：`order=[0,1]` 的三个 phase 在 BI-V150 上均没有降低 Q buffer 的 shared-store
冲突；其 96 次/每 block 每轮是 `order=[1,0]` phase 2/4 的 6 倍，且高于
`order=[1,0]` phase 1 的零冲突。该方向不进入 production。表中的 shared-load 是探针自身读回校验产生，不能代表 QK 矩阵 consumer 的 shared-load 行为。

### 8. CoreX C++ 与 BF16 矩阵指令接口边界

对当前 CoreX SDK 的公开 C/C++ 接口和示例进行了
全文搜索，没有发现可由 CUDA C++ 直接调用的 BI-V150 BF16 matrix/mma intrinsic 或官方
示例。公开 SDK 的 `llvm/IR/IntrinsicImpl.inc` 中则列出了后端 LLVM intrinsic，包括
`llvm.bi.matrix.mad.f32x4.bf16x4`，以及 `m8n16k32`、`m8n64k32` 等 BF16 矩阵形式。

结论：当前安装包证明 BI-V150 LLVM 后端具备这些矩阵指令，但没有随 SDK 提供对应的
C++ 调用封装。普通 `.cu` 可以精确验证 shared-memory 地址映射和 bank conflict，却不能
在不额外编写 LLVM IR 或获得厂商 API 的情况下，直接构造“手工 shared layout + BI matrix
instruction”的 C++ 矩阵探针。该结论是当前安装包接口边界，不代表硬件不支持矩阵指令。

#### 外部 `llc` 不能重编译当前 Triton LLIR

尝试使用 `/usr/local/corex-4.4.0/bin/llc -march=bi -filetype=obj` 重编译当前 Triton 生成的 LLIR 时失败。失败点位于 kernel 函数参数属性
`captures(none)`，该 `llc` 报 `expected ')' at end of argument list`。

结论：当前 CoreX 命令行 `llc` 的 IR 语法能力与正在生成 LLIR 的 Triton 内置编译链不兼容；
不能把 Triton dump 的 LLIR 直接交给该外部 `llc` 编译为可执行 probe。此项是工具链接口
限制，未对硬件矩阵指令能力作出负面结论。

#### 当前 Triton 后端的实际重建边界

安装包中存在 Iluvatar 后端的 CMake 子目录和部分后端源码，运行时同时
存在 `/usr/local/lib/python3.12/site-packages/triton/_C/iluvatarTritonPlugin.so` 与
`libtriton.so`，但安装包中没有完整的 Triton 顶层构建工程。

**结论闭合：** 不能仅在后端子目录独立重建插件，也不能把“改 Q `useSme=0` 的
shared-layout lowering”写成当前可用优化。未取得与运行时匹配的完整构建工程前，不要改已安装 plugin。
